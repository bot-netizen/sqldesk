What it is for

A query editor your whole company can read from

SQLDesk connects to the databases you already have, lets the people who write SQL answer questions with it, and puts those answers in front of everybody else — on a dashboard, in an alert, or through an agent. You run it yourself, and nobody pays per person who looks.

Six decisions, and what each one costs us

Every one of these is a choice with a downside. They are written here with the downside attached, because a list of advantages with no costs is a sales page.

01

Viewers are free, and always will be

No seat count, no viewer tier, no licence server to call. A dashboard read by four hundred people costs exactly what one read by four costs: the box you run it on. The cost of that decision is that there is no hosted tier to buy — somebody has to run Postgres, Redis and a container, and that somebody is you.

One docker compose up, or helm install for a cluster.

02

It does not phone home

Not a policy, a removal: the hard-coded endpoints that posted usage statistics, and separately an administrator's name and email, are gone from the code. Version checking exists and is off until you point it at an endpoint you control. The cost is that we learn nothing about how SQLDesk is used unless somebody tells us.

No outbound request SQLDesk makes is to us.
SQLDESK_VERSION_CHECK_URL is empty by default.

03

One permission model, for people and for agents

A group's access to a data source decides what its members see in the editor, on a dashboard, in an alert, in an export — and through MCP, where an agent runs as the person whose key it is and can reach nothing they could not. There is no service account and no way to configure one, because a tool server with more access than its user is a way to launder permissions. The cost is that an agent is sometimes refused where a shared credential would have worked.

04

Numbers, not adjectives

Work on the query path is measured before and after, on real data volumes, and the figures are published with the method — including the changes that turned out not to matter. The cost is that it is slower to claim anything: a figure nobody has measured does not go on a page.

05

Apache 2.0, with the provenance kept straight

A permissive licence with an explicit patent grant. SQLDesk is built on top of Redash, and the inherited code keeps its original copyright and licence text, reproduced in full — because the alternative is a licence violation dressed up as a rebrand.

LICENSE → Apache 2.0  ·  LICENSE.redash → BSD 2-Clause, verbatim
NOTICE → attribution, and an explicit "not affiliated" statement

06

One deployment, not four stitched together

Queries, dashboards, alerts, Kafka streams and an MCP server, under one login and one permission model. A stream's window is a table you can join against; a saved query is something an agent can find, read and extend; a dashboard is a page you can verify and subscribe to. The cost is breadth: a specialist tool will beat any single surface here, and if one of these is your whole problem, use the specialist.

Who it is for

A team with a warehouse and no BI budget

Somebody writes SQL; everybody else needs the answer. Thirty-five data sources, charts on top of results, scheduled refreshes and alerts, with no per-person cost.

Anyone who cannot send data to a SaaS

Health, finance, government, or simply a policy. Nothing leaves the network, the credentials stay encrypted in your own Postgres, and the only outbound requests are to your own data sources.

People putting agents near their data

An MCP server with the catalog behind it: an agent finds the query somebody already wrote, reads what a table is for, and runs one read as the user whose key it holds — with every call audited.

Teams with a Kafka topic nobody can query

Point SQLDesk at the topic and the last few minutes become a table, with per-minute rollups behind it. JSON, Avro and Protobuf, with or without a schema registry.

What it is not

Worth saying plainly, so nobody installs it expecting one of these.

Not a point-and-click question builder

SQLDesk assumes somebody on the team writes SQL. Everybody else reads what they wrote, changes its parameters and subscribes to it.

Not an infrastructure monitoring tool

It queries Prometheus and Mimir like any other source, but alerting on infrastructure metrics at second resolution is not what this is built around.

Not a streaming engine

A bounded window of a Kafka topic, kept in DuckDB and rolled up. Continuous queries and push-based updates over a persistent connection are a different product.

Not a notebook

A query is a query, with a chart and a history. Mixing prose, Python and SQL on one canvas is on the roadmap rather than in the product.
