# 0.6 plan — an AI layer, on top of what SQLDesk already knows

Four surfaces — an MCP server, a chat assistant, an optimize button and a
semantic layer — are clients of one context service built from warehouse
metadata and SQLDesk's own query history. Build the context service first;
the rest are thin on top of it.

The original plan is in the shared doc, "AI layer for Redash — build plan".
This file is that plan with the decisions settled and the corrections that
came out of reading it against this codebase rather than against Redash in
the abstract.

## Settled before starting

Two of the original open questions were already answered by history:

- **Fork or build fresh.** Forked, and 0.5 shipped from it. Nothing to decide.
- **Naming.** SQLDesk. The MCP server and package names follow it, and the old
  Redash names stay accepted where they already are.

Two more this plan settles:

- **The MCP server is a separate optional process.** Same shape as the alert
  screenshot renderer in 0.5: its own container, off unless configured, and
  the published image does not grow by a byte for people who never turn it on.
- **Claude Desktop first, in-app chat second.** Desktop gives signal in days
  with no frontend work and no session to arrange, and it forces the tool
  boundary to be honest. Building the in-app chat first would let retrieval
  logic leak into the frontend, and then there are two implementations of it
  forever.

Still open:

- [ ] Which source is the pilot. Iceberg through Trino has the richest
      metadata and is the best first target.
- [ ] Hosted model, local model, or both from day one.
- [ ] How the catalog handles going stale: `harvested_at` exists, a policy
      does not.

## Architecture

One context service between the data sources and every AI surface. Nothing
else touches raw schema.

```
data sources ─┐
              ├─► harvester ─► catalog (Postgres) ─► context service ─┬─► MCP server ─┬─► Claude Desktop
query history ┘                                                      │               └─► in-app chat
                                                                     └─► optimize button
```

Every call executes as the signed-in user and honours the existing data source
and group ACLs. No service account with blanket access.

**That is an assumption to test, not a given.** 0.5 found `JobResource.delete`
with no permission check at all — any authenticated user could cancel anyone's
running query. An MCP `run_query` would be the highest-risk endpoint this
project has ever shipped, and it deserves a permission test per tool before it
ships, not after.

## Phase 0 — the context service

No AI in this phase. It ships on its own as better schema search, and
everything later depends on it.

### The harvester

One adapter per source type, on a schedule, writing into Postgres. Today's
`get_schema()` holds table, column and type; this goes well past that —
partition specs, sort orders, per-column cardinality and null fractions,
distribution keys, row counts.

**Not thirty-five adapters.** `BaseQueryRunner` gets an optional method that
defaults to what `get_schema()` already returns, so every existing runner
keeps working untouched and the rich sources opt in one at a time. "Every data
source harvests on a schedule" as a phase-0 exit condition is a thirty-five
runner commitment and the wrong shape for this codebase.

**It runs as an RQ periodic job**, registered in `tasks/schedule.py`, like
every other scheduled thing here. Not a new scheduler.

### Mining the query history

The highest-value input in the plan, and the one thing a competitor cannot
ship in a year: the join graph, column importance, filter conventions, and a
few-shot corpus of working SQL written by this team on these tables.

**It is worth nothing on day one.** A fresh install has no query history, so
this is not a launch feature -- it is the thing that makes the product better
the longer it is used. Everything that ships on day one has to work from
harvested schema alone. Say that out loud when planning, because the plan
reads as though the log is already there.

**Read it from `queries.query_text`, not from `events`.** 0.5's admin work
established that scheduled refreshes never reach `events` — they go
`refresh_queries` → `enqueue_query`, not `run_query`. Mining `events` gets
ad-hoc runs only and silently under-weights everything on a schedule. Use
`events` for who ran what and when; use the saved query text for structure.

**Parameters will break the parser.** Saved SQL here is Mustache: a query
holding `{{ region }}` is not parseable SQL, and both the few-shot corpus and
every sqlglot path will trip on it. Render or strip parameters before parsing.

### The catalog

New tables in the existing Postgres: `catalog_table`, `catalog_column`,
`catalog_relationship`, `catalog_card`, `semantic_metric`, `optimizer_finding`,
`ai_session`.

**All of them carry `org_id`.** Every model in this codebase is org-scoped and
these are no exception.

**Ranking starts without pgvector.** The original plan puts a `query_embedding`
table in the metadata database, which makes an extension that managed Postgres
providers may not offer a hard dependency of the whole feature. Postgres
full-text search is already wired up here (`7ce5925f832b`). Ship BM25 plus
usage-frequency weighting first; add vectors when the eval set says they earn
their dependency.

**Done when** the pilot source harvests on a schedule, the join graph is
queryable, and a keyword search over tables and columns returns ranked results.

### The eval set, in this phase

Fifty to a hundred question-to-SQL pairs, before any retrieval work. Without
it there is no way to tell whether a retrieval change helped, and tuning
happens by vibes. 0.5 spent an afternoon on tests that had been quietly wrong
for weeks because nothing measured them.

**Written by hand, not mined.** The original plan said to mine them from the
query log, which assumes a query log. A new install has none. This is a day of
somebody's time against the pilot dataset, and it is still the right call --
it is just no longer free.

## Phase 1 — the optimize button, deterministic half

Moved ahead of the MCP server, because it needs neither the catalog nor a
model: sqlglot, EXPLAIN, and the runtime history already stored.

Structured findings with severity — missing partition predicate, implicit cast
on a join key killing partition pruning, `SELECT *` on a wide columnar table,
ORDER BY without LIMIT, a correlated subquery that wants to be a window
function. Rule packs per engine, because Trino, StarRocks and Vertica fail in
genuinely different ways.

This is the cheapest real value in the whole plan and carries no AI risk.
Check sqlglot's dialect coverage against the pilot engines before committing
to it.

## Phase 2 — the MCP server

Tools are task-shaped, not CRUD-shaped: `find_context(question)` returns
ranked tables with columns already pruned plus two or three similar past
queries, so the model makes one call instead of forty. `expand_table`,
`find_similar_queries`, `validate_sql`, `run_query`.

Serialization is DDL-shaped rather than JSON — JSON repeats its keys per
column and costs roughly three times as much. Inline value enumerations for
low-cardinality columns matter more than they look: without them a model
writes `status='complete'` and the query silently returns no rows.

Guards: EXPLAIN before execute, hard row and byte caps, stable ordering and a
fixed prompt prefix so prompt caching hits.

## Phase 3 — the LLM half of the optimizer

Input is the original SQL, the findings, the schema slice and the dialect.
Output is a rewrite with a per-change rationale mapped to a finding.

**Verification is the product.** Normalize and parse both, EXPLAIN both,
run both against one partition and compare row count and a sorted hash — then
label the outcome honestly: "verified equivalent on one day of data" against
"not verified, review manually". That labelling is the whole difference
between this and the optimizers that confidently return a query producing
different numbers.

## Phase 4 — chat, then a semantic layer

Chat is a second client of the same MCP tools. Every identifier in generated
SQL is checked against the catalog after parsing, so a hallucinated column
fails closed. Assumptions are always surfaced.

For the semantic layer, keep two things separate: a catalog (descriptions,
glossary, lineage, ownership) and metric definitions that compile to SQL. Do
not take a hard dependency on Cube or MetricFlow early — define a thin
internal interface for metric and entity, back it with our own tables, and
shape the interface so one of them can slot in behind it.

## Risks

**Cost exposure from the chat path.** A generated query can scan a petabyte.
Needs a queue dedicated to AI-issued queries, byte-scanned limits, and
confirmation before anything expensive runs.

**On-prem buyers will not send schema and sample values to a hosted model.**
A per-data-source AI toggle, PII column tagging so value samples are
suppressed, and a local model path. Gating for the finance and ad-tech
buyers, not a nice-to-have.

**The moat is the history, not the model.** An MCP exposing a catalog and a
query runner is a commodity within a year. What is hard to copy is the query
history, the permissions model, the saved queries and the dashboards. Favour
the features that only work because those exist.

**And the plan is entirely query-centric.** Dashboards and alerts are the
product. "This dashboard breaks if you rename that column" appears once, in
the original's risk list, and is the most SQLDesk-only feature in the whole
document. It belongs in a phase, not a footnote.
