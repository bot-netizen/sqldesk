Notebooks

A chain of cells, where everything else in SQLDesk ends in one SELECT. Pull this, join it to that, reshape it, look — with the data source permissions, the result store and the scheduler you already have.

What a notebook is for

The work a saved query cannot hold. People do it in Jupyter today, and when they do, the warehouse never hears about it: the lineage, the permissions and the scheduling all stop at the edge of somebody’s laptop. A notebook keeps that work where the rest of your data lives.

A notebook is a draft until you publish it, the same promise queries and dashboards make. What you are still building is not in anybody else’s list.

Cells

Cells are named, never numbered. A later cell refers to this one by name — as a relation in SQL, as a dataframe in Python — so inserting, deleting and reordering leave every reference pointing at what it meant. A name is letters, digits and underscores, not starting with a digit, because it has to be legal as a table name and as a variable at the same time.

A SQL cell

A SQL cell is one of two things, and which one it is follows from whether you give it a data source:

  • With a data source it queries that warehouse, under the permissions that data source already has. A notebook is not a way round them.
  • With no data source it reads earlier cells, which are relations: SELECT count(*) FROM orders where orders is the cell above.

It cannot be both, and the cell says so before you run it. A warehouse has never heard of a cell called orders, and SQLDesk is not going to push four million rows into it to pretend otherwise.

A Python cell

A Python cell computes; it cannot query. It reads an earlier cell’s output as a pandas dataframe under that cell’s own name, and nothing else. That is the strongest rule in the design, for what it removes: no credential ever reaches the interpreter, because there is nothing for it to reach. Anything that needs the warehouse needs a SQL cell above it.

Variables persist between cells, as they do in Jupyter: df assigned in one cell is still there five cells later. If the last line of a cell is an expression, its value is the cell’s output — a dataframe becomes a relation later cells can read, and anything else is text to look at.

Python cells need an interpreter, which is off by default. Without one, the cell says so rather than failing when somebody runs it.

Stale, and why nothing is corrected for you

A notebook with a session is a notebook that can rot: the number in cell four was computed from cell one, cell one has been edited and re-run twice since, and nothing on the page says so. That is the normal failure of every notebook tool with hidden state.

So every run records which cells it read, and a cell whose inputs have re-run since is marked stale — and left exactly as it was. The number on the screen is still the number that was computed; re-running it is your decision. Staleness carries: if A feeds B and B feeds C, re-running A marks both.

A cell whose input was deleted says something different, because it is a different problem: that one cannot be reproduced at all, where a stale one only needs re-running.

What is kept, and what is thrown away

Three things, with three different lifetimes:

  • the output on the page — a truncated slice, kept with the notebook, which is why reopening one draws instantly and attaches nothing;
  • the handoff between cells — the whole result, in a DuckDB file of the notebook’s own, thrown away and rebuilt by re-running;
  • the record of each run — which cells it read, how long it took, how many rows — kept for ever, because that is what makes staleness answerable.

The table under a cell shows the slice and says what it is a slice of: first 1,000 of 4,200,000 rows. The next cell reads the whole thing, not what you can see.

Archiving a notebook keeps all of it except the handoff, which re-running rebuilds.

A chart on a cell

Any cell that produced a table can carry a visualization, with the same editor and the same chart types as a query. It is drawn from the rows on the page rather than the whole handoff — a chart of four million points is a smear.

A cell’s chart cannot yet become a dashboard widget. Refreshing a widget backed by cell seven means running cells one to seven, on an interpreter, on a dashboard’s refresh interval — that is a scheduling design rather than a widget, and it is not in this release.

Running and stopping

A cell runs on a worker, like a query, and a SQL cell takes a query slot from its data source’s pool like any other query — the warehouse’s connection limit does not get larger because something was typed into a notebook.

Stop cancels the cell that is running and does not start the next. It does not throw the notebook away: the variables earlier cells assigned are still there afterwards. A cell that ignores the interruption entirely is ended after a few seconds, and the page says that is what happened.

Turning Python cells on

Python runs in a container of its own — never in the worker, which is the process holding every data source’s decrypted credentials. It is built and run only by installs that want it:

docker compose --profile notebooks up executor

Then point SQLDesk at it with SQLDESK_NOTEBOOK_EXECUTOR_URL and give both sides the same SQLDESK_NOTEBOOK_EXECUTOR_TOKEN. Deny that container egress and give it a memory limit: the design makes the first free, since a code cell has nothing it needs to reach, and the second is the real ceiling on what one cell can spend.

Who may use notebooks at all is a permission an administrator grants per group, under Groups, like the other features.

Python on a Spark cluster

Build the interpreter with a Spark Connect client and point it at your cluster:

docker compose build \
  --build-arg WITH_SPARK=true \
  --build-arg SPARK_VERSION=3.5.3 executor

with EXECUTOR_SPARK_REMOTE=sc://your-gateway:15002. The version has to match the cluster: Spark Connect’s client and server are versioned together, and a mismatch shows up as a protocol error on the first call rather than at build time.

Python cells then have spark, which opens a session on the cluster the first time a cell reaches through it — opening a notebook, and running cells that never mention it, open nothing.

A Spark DataFrame returned by a cell is collected to become that cell’s handoff, which is the one moment the cluster’s answer has to fit in one container. It is bounded, and a result over the bound is refused with a sentence rather than quietly cut down — a notebook that showed you the first million rows of a billion without saying so would be worse than one that said no. Aggregate in Spark before returning.

Note what changes when Spark is configured: the interpreter now needs a route to the cluster, so “no egress” becomes “egress to the cluster only” — and that is only as true as whatever enforces it. In Kubernetes, a NetworkPolicy whose single egress rule is the Spark service says it exactly.

What a notebook will not do

  • Write back to a data source. This release is read-and-look.
  • Let a code cell query. Data comes from an earlier cell or not at all.
  • Run on a schedule. Cells run when somebody runs them.
  • Put a cell on a dashboard. See charts for why.
