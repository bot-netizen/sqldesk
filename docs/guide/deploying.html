Deploying

Five processes and two databases — see Architecture. Everything below is a way of arranging those, plus two add-ons that stay off until you ask for them.

Services: what is core, what is an add-on

The core always runs. Each add-on is one decision; leave it off and nothing about it is pulled, started or shown.

ServiceWhat it doesCore or add-on
serverThe web application and the API, including /mcp when MCP is on.Core
workerRuns queries and schema refreshes, and nothing else. Also takes MCP's queue, last, so it is never left unserved.Core
periodic-workerEverything that is not a query: deciding what to refresh, evaluating alerts, sending mail, the clean-ups. Separate since 0.7.7 — see below.Core
schedulerPuts scheduled refreshes, clean-ups and the catalog harvest on the queue. One is enough; more than one is safe.Core
PostgresSQLDesk's own database: users, queries, dashboards, results, the catalog. Not your warehouse.Core
RedisQueues, locks and a schema cache. Losing it costs in-flight jobs and nothing else.Core
mcp-workerTakes only the queries a model asks for, so a model exploring cannot hold up a dashboard.Add-on: MCP & Catalog
stream-workerConsumes Kafka topics into the windows a stream query reads. Workers of its own, because a consumer holds one for minutes rather than seconds.Add-on: Streams
screenshotsA headless browser that draws dashboards and charts for alert emails. Holds no credentials and keeps no state.Add-on: Rendering
Shared volumeNot a process. Uploaded files and stream windows: one process writes, another reads. Created when Uploads or Streams is on.Add-on
Why queries and housekeeping are on different workers

A query can hold a worker for minutes. With everything on one worker, two slow queries meant nothing was deciding what to refresh, nothing was evaluating alerts and nothing was sending mail — while every health check still passed, so the only symptom was staleness nobody could account for.

The housekeeping work is not heavy; it is a few seconds a minute. What it needs is to be running, which is exactly what it was not. Set periodicWorker.enabled=false and its queues go back to the ordinary worker rather than being stranded — no scheduling at all is a worse failure than a slow query, because nothing reports it.

What is on when you change nothing

Everything that costs something while nobody is using it is off. A default install is five deployments and one volume, and the published image is the same size whichever of these you turn on — the only one with an image of its own is the renderer.

A permission nobody can use is worse than no permission

streams.enabled tells the application as well as the cluster. With it off, the Streams permissions are not offered to any group, the streaming halves of the Queries and Dashboards menus are not drawn, and neither is the Settings tab — rather than leading somebody to pages that quietly never fill, because nothing is taking from the streams queue.

Mailpit and the demo warehouse in the development compose file are for developing SQLDesk, not for running it, and appear in neither of the files below.

MCP & Catalog

One switch turns on the MCP endpoint, the catalog it answers from, the scheduled harvest, measures, Admin → Catalog and manage ai export/import. Off, /mcp answers 404 and the Catalog page is not there. SQLDesk calls no model itself either way: the model is the MCP client's.

# .env
SQLDESK_FEATURE_AI=true
SQLDESK_MCP_QUEUE=mcp           # optional, with the mcp profile: MCP's own worker
COMPOSE_PROFILES=mcp
helm upgrade --install sqldesk ./charts/sqldesk --set mcp.enabled=true

Then fill the catalog once, rather than waiting for the daily harvest: /app/manage.py ai harvest in the server container.

Streams

Kafka topics you can query — see the Streams guide. One switch turns on the consumers, the Streams permissions, the streaming halves of the Queries and Dashboards menus, and Settings → Streaming Data Sources.

helm upgrade --install sqldesk ./charts/sqldesk --set streams.enabled=true

Two settings have to agree, and the lower of them wins. streams.worker.workersCount is how many processes exist; SQLDESK_STREAM_MAX_CONCURRENT is how many topics may consume at once. A slot limit of five served by two processes is a limit of two wearing a five.

helm upgrade --install sqldesk ./charts/sqldesk \
  --set streams.enabled=true \
  --set streams.worker.workersCount=5 \
  --set extraEnv.SQLDESK_STREAM_MAX_CONCURRENT=5

A slot is a topic, not a viewer: five people watching orders share one consumer, one window and one slot. Turning streams on also creates the shared volume, because the window is a file the stream worker writes and the server reads.

Uploads

CSV and Parquet files people upload and query with DuckDB.

helm upgrade --install sqldesk ./charts/sqldesk --set uploads.enabled=true

The claim is ReadWriteOnce by default, which mounts on one node — so with it the chart keeps the workers on the server's node, or they wait forever on a Multi-Attach error. If you intend to spread pods across nodes, give it a ReadWriteMany class (EFS, Filestore, Azure Files, NFS) and say so:

--set uploads.accessMode=ReadWriteMany --set uploads.storageClass=efs-sc

Files expire on a clock people can see and stop — uploads.lifecycle — because an uploaded file is the only copy there is, unlike a query result the warehouse can be asked for again.

Rendering

Pictures of dashboards and queries in alert emails. The renderer is a browser, which is why it is its own image (ghcr.io/bot-netizen/sqldesk-screenshots) and not part of the SQLDesk one.

# .env
SQLDESK_FEATURE_ALERT_SCREENSHOTS=true
SQLDESK_SCREENSHOT_URL=http://screenshots:3000
SQLDESK_INTERNAL_BASE_URL=http://server:5000
COMPOSE_PROFILES=rendering      # mcp,rendering for both
helm upgrade --install sqldesk ./charts/sqldesk --set rendering.enabled=true

The chart sets the three variables itself. The renderer reaches SQLDesk on the internal network rather than your public address, so redirect to HTTPS at your proxy and leave SQLDESK_ENFORCE_HTTPS off — with it on, the renderer is redirected to an address it cannot reach and every picture fails. Cookies are still marked Secure: that follows from SQLDESK_HOST starting with https://, not from the redirect.

The renderer is a browser, so it renders only SQLDesk's own address, and only for a caller that shows a token. The chart generates the token; with Compose, set SQLDESK_SCREENSHOT_TOKEN in .env (the renderer checks it whenever it is set).

Put COMPOSE_PROFILES in .env rather than passing --profile. A later pull or up without the flag would leave the add-on behind on the old version.

What must be set

VariableWhy
SQLDESK_COOKIE_SECRETSigns sessions. The server refuses to start without it.
SQLDESK_SECRET_KEYEncrypts data source credentials. Changing it makes existing ones unreadable.
POSTGRES_PASSWORDCompose only: the bundled Postgres's password, which the compose file builds the database URL from.
SQLDESK_DATABASE_URLSQLDesk's own Postgres, not your warehouse. Set for you by both files below.
SQLDESK_REDIS_URLQueues and cache. Set for you by both files below.
SQLDESK_HOSTThe address in emails and alert links.

Keep the two secrets somewhere they survive a redeployment. Losing the cookie secret logs everyone out; losing the secret key loses every stored credential. Set both: with SQLDESK_SECRET_KEY unset, the cookie secret encrypts credentials too, and rotating it for sessions then loses them.

Both files also turn on CSRF checks (SQLDESK_ENFORCE_CSRF), which upstream leaves off so as not to break old installs. The application has always sent the token; API-key calls, MCP included, are not affected.

Limits worth knowing about

Three defaults changed in 0.7.7, each because the old value was "no limit" and no limit is a way for one query to cost an install its capacity while every health check still passes.

VariableDefaultWhat it does
SQLDESK_ADHOC_QUERY_TIME_LIMIT900 Seconds a query somebody is waiting for may run. Fifteen minutes is long enough for an unindexed join over a year of events or a first read from cold storage, and short enough that a runaway query is not still holding a worker after lunch. Raise it if your warehouse is genuinely slower; -1 is no limit, as before.
SQLDESK_SCHEDULED_QUERY_TIME_LIMIT1800 The same for a scheduled run, which nobody is sitting in front of.
SQLDESK_MCP_WRITES_PER_DAY50 How many catalog descriptions, measures or saved queries one person's API key may write through MCP in a day. An agent told to describe a warehouse will describe the whole warehouse; this keeps a mistake to a morning's review. 0 is no limit.

A query stopped by its limit says so, and the limit is per install rather than per query — if one report legitimately takes an hour, schedule it rather than raising the ad-hoc limit for everybody.

Running more at once

Two numbers decide how much SQLDesk does at the same time, and the first one is read wrongly more often than not.

VariableDefaultWhat it does
SQLDESK_WORKERS_COUNT2 How many queries run at once. This is concurrency, not a rate.
SQLDESK_WEB_WORKERS4 Threads serving the API and the pages. Raise it for more people browsing, which is a different pressure from more queries running.

Two workers is not two queries a second. It is two queries in flight. With a query that takes 100ms that is about twenty a second; with a query that takes a minute it is two a minute. So the number to raise is the number of queries you want running together, and the thing that tells you whether it is too low is queries sitting in the queue, not a rate.

The ceiling is rarely this setting. Every running query holds a connection to its data source for as long as it runs, so the warehouse's own connection limit is the real limit — sixteen workers against a Postgres allowing ten connections gets you six failures, not six more queries. Raise them together, and remember the scheduled runs are in the same pool.

Since 0.7.7 the housekeeping queues — scheduling, alerts, mail, the cleanups — belong to a worker of their own, so slow queries can no longer starve them. On Kubernetes that is periodicWorker in the chart; it needs very little and should stay at one replica.

SQLDESK_WORKERS_COUNT=8
SQLDESK_WEB_WORKERS=8

Schema refreshes are the other periodic cost, and the one most worth turning down. Every data source is read on every pass, so on a warehouse with thousands of tables one pass is minutes of work.

VariableDefaultWhat it does
SQLDESK_SCHEMAS_REFRESH_SCHEDULE180 Minutes between background schema refreshes. Three hours since 0.7.8, half an hour before it.

What being stale costs is bounded: autocomplete and the schema browser can be that far behind, and the catalog MCP answers from is harvested off the same cached copy. Running a query is unaffected — the cache is only ever a cache, and a miss reads the warehouse. The cure for "I have just added a table" is the refresh button in the schema browser, which forces a live read of the one source in front of you.

Where one source is much heavier than the rest, leave it out altogether rather than shortening the interval for everything. Its id goes in the Redis set data_sources:schema:blacklist.

Mail

Invitations, password resets and alert emails need a mail server. In .env:

SQLDESK_MAIL_SERVER=smtp.example.com
SQLDESK_MAIL_PORT=587
SQLDESK_MAIL_USE_TLS=true
SQLDESK_MAIL_USERNAME=…
SQLDESK_MAIL_PASSWORD=…
SQLDESK_MAIL_DEFAULT_SENDER=sqldesk@example.com

Then send yourself one to check it arrives: docker compose -f compose.prod.yaml run --rm server manage send_test_mail you@example.com. Without mail, people are invited with a link an admin copies to them by hand.

OAuth for MCP clients

On wherever MCP is on, and it needs nothing configured: a client discovers the endpoints from the 401 it gets on its first call, opens a browser, and the person signs in the way they always do. See signing in.

It needs https. An authorization code and a bearer token crossing a network in the clear is what the flow exists to avoid, so the endpoints refuse plain http. Behind a TLS-terminating proxy this works as long as the proxy sets X-Forwarded-Proto, which every ingress does; the hop SQLDesk itself sees is http and PROXIES_COUNT is what says how many hops to trust.

VariableWhy
SQLDESK_MCP_OAUTH_ENABLEDDefault true where MCP is on. Off, the discovery endpoints answer 404 so a client falls back to an API key rather than looping on an error it cannot act on — and tokens already issued stop working, because turning it off should mean something.
SQLDESK_MCP_OAUTH_ALLOW_HTTPDefault false. The one honest use is a local install reached over a port-forward with no TLS anywhere. The server logs a warning for as long as it is set.
SQLDESK_PROXIES_COUNTHow many proxies are in front. Decides how far back X-Forwarded-For and X-Forwarded-Proto are trusted.

Tokens expire in an hour and refresh for thirty days of use. They are stored as hashes, listed on each person’s profile under Connected apps, visible to administrators under Admin → MCP, and revoked when an account is disabled. API keys keep working, which is what a script or a headless setup should use.

Scheduled subscriptions, and sending to Slack

Both need the renderer add-on — there is nothing to send without a picture — and the Send dashboards permission, which an administrator grants to a group. Where no renderer is configured the feature is not offered at all, rather than offered and failing.

The renderer is a separate optional container (rendering.enabled=true in the chart, or the commented-out service in compose.prod.yaml). It reaches the application by the internal service name, not the public address, so it does not have to get through whatever is in front of you:

VariableWhy
SQLDESK_FEATURE_ALERT_SCREENSHOTSTurns rendering on. Set for you when the chart's rendering.enabled is true.
SQLDESK_SCREENSHOT_URLWhere the renderer is. The chart points it at its own Service.
SQLDESK_INTERNAL_BASE_URLHow the renderer reaches the application. The Service name, not SQLDESK_HOST, which may be behind SSO the renderer cannot get through.
SQLDESK_SCREENSHOT_TOKENShown to the renderer with every request, so only the worker can ask it to fetch a page.

Nothing has to be made public to be pictured. The renderer is let in with a pass good for one dashboard, for five minutes, read-only, and spent as soon as the picture is taken.

Sending to a Slack channel needs one more thing: an app installed in the workspace, with its bot token pasted under Settings → Slack. SQLDesk draws the picture and uploads it, so Slack never has to reach this install — which is what makes it work behind a VPN. Scopes: chat:write, files:write, channels:read, groups:read.

Docker Compose

cp .env.example .env        # then fill in the secrets and POSTGRES_PASSWORD
docker compose -f compose.prod.yaml run --rm server create_db
docker compose -f compose.prod.yaml up -d

The tables first, then the services: a server started against an empty database answers every page with an error. Open the address and the first page makes your organization and your administrator account.

Pin the image in .env as SQLDESK_IMAGE=. Without it the compose file falls back to the release it was written for.

The port is published on the machine itself (127.0.0.1) until you put a proxy in front or set SQLDESK_BIND=0.0.0.0. Tell SQLDesk how many proxies stand in front of it with SQLDESK_PROXIES_COUNT: 0 when it is reached directly, 1 behind nginx or Caddy. The number decides which address the login throttle and the audit log see.

Upgrading

# .env: SQLDESK_IMAGE=ghcr.io/bot-netizen/sqldesk:0.7.10
docker compose -f compose.prod.yaml pull
docker compose -f compose.prod.yaml run --rm server manage db upgrade
docker compose -f compose.prod.yaml up -d

Migrations before the new server takes traffic. Release notes call out any migration that rewrites data rather than adding to it. The chart does this itself, as a hook that runs before anything else changes.

0.6 → 0.7

One migration, one default that changed, and one thing you have to ask for.

Docker Compose. Pin the image, migrate, then start:

# .env
SQLDESK_IMAGE=ghcr.io/bot-netizen/sqldesk:0.7.10

docker compose -f compose.prod.yaml pull
docker compose -f compose.prod.yaml run --rm server manage db upgrade
docker compose -f compose.prod.yaml up -d

Helm. The chart migrates itself, in a hook that runs before anything else changes:

helm upgrade sqldesk ./charts/sqldesk --reuse-values \
  --set image.tag=0.7.10

The last migration stays as the Job sqldesk-migrate, with its log, until the next upgrade replaces it. Before 0.7.5 every upgrade left a Job of its own behind, named with the revision; remove those once:

kubectl get jobs -o name | grep -E '/sqldesk-migrate-[0-9]+$' | xargs kubectl delete
If people upload files, say so on the command line

uploads.enabled defaulted to true in 0.6 and defaults to false in 0.7, so that an install which never uploads anything carries no volume and its workers are free to schedule anywhere. An install that was using the default therefore has nothing for --reuse-values to carry forward, and the upgrade turns uploads off: the volume stops being mounted, and an upload fails.

The files themselves are safe — the claim is annotated helm.sh/resource-policy: keep, so Helm leaves it alone — and adding --set uploads.enabled=true brings it back exactly as it was. Add it to the upgrade if anyone uses uploads:

helm upgrade sqldesk ./charts/sqldesk --reuse-values \
  --set image.tag=0.7.10 \
  --set uploads.enabled=true

The migration adds kind to dashboards and fills it in with the rule 0.6 applied when reading: a dashboard with a streaming panel becomes a streaming dashboard, everything else an ordinary one. No dashboard changes which list it appears in. It is reversible; the downgrade drops the column.

Streams are off until you ask for them — streams.enabled=true in the chart, or SQLDESK_STREAMS_ENABLED=true with a stream worker on Compose. Left off, the Streams permissions are offered to nobody, the streaming halves of the Queries and Dashboards menus are not drawn, and the Settings tab for topics is not there. See Streams.

Nothing else changes an existing dashboard, query or data source. The navigation moved — streaming is a half of Queries and a half of Dashboards rather than a section of its own — and the four /streams/… URLs from the old menu redirect to where those pages live now, so links people have already sent each other still work.

Rolling back to 0.6 means putting the old image back and running manage db downgrade once. Dashboards lose the kind column and 0.6 works out the kind from the widgets again, as it did before.

Everything on, for trying it out

Each add-on is off so that an install pays for nothing it does not use. To see all of them at once — on a laptop, with nothing real attached — turn them all on together:

helm upgrade --install sqldesk ./charts/sqldesk \
  --set image.tag=0.7.10 \
  --set streams.enabled=true \
  --set mcp.enabled=true \
  --set uploads.enabled=true \
  --set rendering.enabled=true

That adds a stream worker, an MCP worker, the shared volume, and the headless browser that draws pictures for alert emails. On a four-core laptop it is comfortable; see How much machine you need for what each part asks for.

Streams need something to consume. There is a toy broker in the repository — one Redpanda node and two producers, a message a second each on orders and payments:

kubectl apply -f examples/kafka-demo.yaml

Then add a data source of type Kafka stream with the broker redpanda:9092, and turn the topics on under Settings → Streaming Data Sources. An administrator may use every feature the install offers without granting anything; for everybody else the permissions are handed out per group under Settings → Groups.

Streams are Kubernetes-only in 0.7

compose.prod.yaml has no stream worker and its worker does not take from the streams queue, so a Compose install cannot consume a topic however the environment is set. Everything else — MCP, uploads, the renderer — runs there: uploads need no switch at all, and the other two are profiles.

# .env
SQLDESK_FEATURE_AI=true
SQLDESK_MCP_QUEUE=mcp
SQLDESK_FEATURE_ALERT_SCREENSHOTS=true
SQLDESK_SCREENSHOT_URL=http://screenshots:3000
SQLDESK_INTERNAL_BASE_URL=http://server:5000
SQLDESK_SCREENSHOT_TOKEN=a-random-string

docker compose -f compose.prod.yaml --profile mcp --profile rendering up -d

Kubernetes

A Helm chart is in charts/sqldesk. It generates the two secrets on first install and keeps them on every upgrade after, so do not pass them on the command line: a second --set secrets.secretKey=$(openssl rand …) would replace the key and every stored credential with it.

minikube start
helm install sqldesk ./charts/sqldesk --timeout 15m \
  --set host=http://localhost:8080
kubectl port-forward svc/sqldesk 8080:5000

Port 8080 rather than 5000, which macOS keeps for AirPlay. minikube service works too, but gives a different random port each time, so host cannot be set to match.

Uploaded files (CSV and Parquet for DuckDB) live on a volume the server and the workers share. It is ReadWriteOnce by default, which every cluster can provide, and the chart keeps the workers on the server's node so they can mount it. With a ReadWriteMany storage class, set uploads.accessMode=ReadWriteMany and they schedule anywhere.

For a real cluster, put an Ingress in front and terminate TLS there — an API key travelling to /mcp over plain HTTP is a credential in the clear — and set service.type to ClusterIP; NodePort is for minikube.

The bundled Redis takes a generated password, and a NetworkPolicy keeps Postgres, Redis and the renderer reachable from this release's pods only. The policy needs a network plugin that enforces it (Calico, Cilium, the managed clouds' own); elsewhere it is accepted and does nothing, which is why the password is there too.

Already running on Compose? Moving from Docker Compose to minikube brings the existing instance across instead of starting an empty one.

On a real cluster

examples/values-production.yaml is the starting point. It was installed as written into a minikube namespace enforcing the restricted Pod Security Standard, with an external Postgres, and every pod was admitted and running. Change the four lines marked CHANGE and install it with the database URL on the command line, so the password stays out of the file:

helm upgrade --install sqldesk ./charts/sqldesk \
  --namespace sqldesk --create-namespace \
  -f examples/values-production.yaml \
  --set "postgres.external=postgresql://USER:PASSWORD@HOST:5432/sqldesk" \
  --timeout 15m --wait
  • Use a managed Postgres. The bundled one is for development, and it cannot run where restricted is enforced: it starts as root, and the usual non-root workaround makes its data directory group-writable, which Postgres refuses to start with. Every other pod in the chart complies.
  • Set host to the https:// address people use. Links in emails are built from it, and it is what makes the session cookie Secure when TLS ends at the Ingress.
  • Raise the Ingress's body size. An upload is up to 200 MB and nginx's default is 1 MB, so every real upload becomes a 413 the application never sees. The example sets it.
  • Back up the generated Secret. secretKey encrypts every data source's credentials; lose it and they are unreadable. kubectl -n sqldesk get secret sqldesk-secrets -o yaml > sqldesk-secret.backup.yaml
  • With Argo CD, make the Secret yourself. The chart keeps its generated secrets by reading them back from the cluster, which it can do under helm install and helm upgrade but not under helm template — and helm template is how Argo CD renders a chart. There it would make a new secretKey on every sync, and every data source's credentials would become unreadable. Create the Secret once and name it in secrets.existingSecret: 
    kubectl -n sqldesk create secret generic sqldesk-secrets \
  --from-literal=cookie-secret="$(openssl rand -hex 32)" \
  --from-literal=secret-key="$(openssl rand -hex 32)" \
  --from-literal=database-url='postgresql://USER:PASSWORD@HOST:5432/sqldesk'
    The bundled Redis then runs without a password, since the chart has nowhere to keep one: keep networkPolicy on, on a cluster that enforces it.
  • The images are public. ghcr.io/bot-netizen/sqldesk pulls without credentials, so no imagePullSecrets are needed.

The first install creates the schema in a Job that Helm runs after the pods start, so the first page may answer with an error for the minute that takes. --wait returns once it has finished. The worker logs tracebacks about missing tables for that same minute — its periodic jobs start before the tables exist — and they stop on their own once the Job is done. Making the pods wait for the schema instead would deadlock --wait, which waits for the pods before it runs the Job.

Moving from Docker Compose to minikube

Everything comes across: people, queries, dashboards, alerts, uploaded files and the credentials saved on data sources. The Compose install's own data is never changed, so it stays your way back until you delete it. Run all of this on the machine running Compose, from the folder with its compose.prod.yaml and .env. It assumes SQLDesk 0.3 or later; upgrade anything older on Compose first. Move to the same release or a newer one, never an older one: migrations only run forward.

1. Back up, while Compose is still running

# The database. -T stops the terminal mangling a binary file.
docker compose -f compose.prod.yaml exec -T postgres pg_dump -U sqldesk -d sqldesk -Fc > sqldesk.dump

# Uploaded files. If it says there is no uploads directory, skip it.
docker compose -f compose.prod.yaml exec -T server tar -C /app -czf - uploads > uploads.tgz

# The two secrets, as the running server has them.
docker compose -f compose.prod.yaml exec -T server python -c \
  "from sqldesk import settings as s; print('cookieSecret:', s.SECRET_KEY); print('secretKey:', s.DATASOURCE_SECRET_KEY)"

# Stop it. No -v: its volumes are your way back.
docker compose -f compose.prod.yaml down

Keep all three private: the dump and the archive are the whole instance, and the secrets unlock every stored credential. Stopping Compose before minikube starts matters too, because two schedulers would run every scheduled query and send every alert twice. If secretKey prints empty, stop here: the chart treats an empty value as "generate one", and no saved credential would decrypt.

2. Start minikube and get the chart

minikube start --cpus 4 --memory 6g
git clone https://github.com/bot-netizen/sqldesk.git

Give Docker Desktop at least 8 GB of memory first; with less, pods get restarted under load. The clone is the latest release, because main only moves at a release. For another one, add --branch and its tag from Releases.

3. Write a values file

# sqldesk-values.yaml -- private, it holds the secrets
secrets:
  cookieSecret: "<cookieSecret from step 1>"
  secretKey: "<secretKey from step 1>"
host: http://localhost:8080
migrations:
  enabled: false   # until the backup is in; step 5 turns it on

Carry over what else you set in .env. mcp.enabled: true if you use MCP; anything the chart has no value for, such as mail, goes under extraEnv: as NAME: value.

4. Install, then restore into the empty database

helm install sqldesk ./sqldesk/charts/sqldesk -f sqldesk-values.yaml --timeout 15m

# Everything but the databases stops, so nothing touches Postgres during the restore.
kubectl scale --replicas=0 $(kubectl get deploy -l app.kubernetes.io/instance=sqldesk -o name | grep -v -e postgres -e redis)
kubectl rollout status deploy/sqldesk-postgres --timeout=10m

kubectl exec -i deploy/sqldesk-postgres -- pg_restore -U sqldesk -d sqldesk --no-owner < sqldesk.dump

Pods erroring between the install and the scale are expected, since there are no tables yet. Migrations are off for the install because on a first install the job creates the current schema, and a backup cannot be restored over it.

5. Migrate, and bring everything back

helm upgrade sqldesk ./sqldesk/charts/sqldesk -f sqldesk-values.yaml --set migrations.enabled=true --timeout 15m
kubectl logs -l app.kubernetes.io/component=migrate --tail=40

The job finds tables already there, so it skips creating them and migrates the restored database to the chart's release. The upgrade then puts every deployment back at its replica count. Set migrations.enabled: true in the values file as well, or the next upgrade turns migrations off again.

6. Uploads, and open it

kubectl rollout status deploy/sqldesk-server --timeout=10m
kubectl exec -i deploy/sqldesk-server -- tar -C /app/uploads --strip-components=1 -xzf - < uploads.tgz
kubectl port-forward svc/sqldesk 8080:5000

Sign in with an existing account. If MCP is on, kubectl exec deploy/sqldesk-server -- /app/manage.py ai harvest fills the catalog now rather than at the first scheduled harvest.

After the move

  • A "create your organization" page means the database is empty: the restore did not land. Do not fill it in. Repeat step 4, read what pg_restore prints, then step 5.
  • A data source that cannot connect probably points at localhost or a Compose service name, which inside minikube mean the pod itself. A database on the same machine is host.minikube.internal.
  • InvalidToken when a data source connects means secretKey is not the key its credentials were encrypted with. Correct it in the values file and run step 5's upgrade again.
  • Going back: minikube stop, then docker compose -f compose.prod.yaml up -d. Compose returns as it was at step 1; nothing done on minikube since is in it.
  • Later upgrades: pull the new release into the clone and run helm upgrade sqldesk ./sqldesk/charts/sqldesk -f sqldesk-values.yaml --timeout 15m. Always pass the values file; --reuse-values on its own carries the old chart's defaults forward.
  • minikube stop and reboots keep the data. minikube delete erases it.

How much machine you need

The figures below are resident memory measured on a running install at idle, not estimates. Add your own headroom: a worker's memory grows with the size of the result it is holding, and a 3 MB result is an ordinary one.

Three shapes

A team, up to about 25 people. The chart's defaults, with a managed Postgres instead of the bundled one. Roughly 2 vCPU and 3 GB for SQLDesk.

A department, about 100 concurrent. Two server replicas, two worker replicas of four processes each, and a Postgres you did not install with Helm. Roughly 6 vCPU and 12 GB.

Set the connection pool before you add replicas

SQLAlchemy's defaults are 5 connections plus 10 overflow per process. Four web workers is up to 60 connections per server replica, and Postgres ships with max_connections=100 — so the third replica is where you meet FATAL: sorry, too many clients already. Either put PgBouncer in front in transaction mode, or cap the pool:

--set extraEnv.SQLALCHEMY_POOL_SIZE=2 --set extraEnv.SQLALCHEMY_MAX_OVERFLOW=3
The warehouse is the real constraint

500 people against Snowflake or BigQuery costs far more than the 22 vCPU above. SQLDesk's job at that size is not to be the bottleneck and to protect the warehouse — which is why a slow data source getting its own queue matters more than web-tier capacity.

Scaling

  • Queries queueing — more workers.
  • Pages slow to load — more web workers, and the connection pool above has to move with them. Since 0.7.7 gunicorn runs gthread with SQLDESK_WEB_THREADS (8) threads per worker: four sync workers meant four requests at a time for the whole install, and several ordinary requests wait on something else for seconds — MCP's run_query, Test connection, sharing to Slack, a stream query. Four slow ones and the fifth person got nothing, the health probe included.
  • The scheduler can have more than one replica (scheduler.replicas). rq-scheduler takes a Redis lock and enqueues only while it holds it, so the others skip the pass: a second pod is a warm spare, not a second copy of every due job. One is the default because that is what every install has been running.
  • Two or more server replicas get a PodDisruptionBudget that keeps one through a node drain. With one replica there is none, deliberately: a budget insisting on keeping one of one blocks the drain and makes a routine node upgrade somebody's problem.
  • Give a slow data source its own queue so it cannot starve the others — see Administration for how, since there is no screen for it yet.
  • A worker being stopped finishes the query it is running, for up to five minutes, before it exits.
  • Uploads pin the workers to one node unless the volume is ReadWriteMany. If you are spreading pods across nodes, that is the setting to check first.

What a connection carries

Since 0.7.7 every connection SQLDesk makes to its own Postgres is checked before it is handed out (SQLALCHEMY_ENABLE_POOL_PRE_PING, on by default). A connection pooled across a Postgres restart, a failover or a proxy's idle timeout is dead in a way nothing notices until a request uses it, and then that request is a 500 for no reason anybody can see.

Connections from the web tier also carry a statement timeout of 30 seconds (SQLALCHEMY_STATEMENT_TIMEOUT_MS). Nothing a request does should take that long — a query against a data source runs on a worker, not here — and without it one lock or one bad plan held a gunicorn worker until gunicorn killed the worker outright, taking every other request it was serving. Workers deliberately do not get one: storing a very large result is a single long INSERT, and cancelling that would fail a query that had already run. Both get an idle-in-transaction timeout (SQLALCHEMY_IDLE_IN_TRANSACTION_TIMEOUT_MS, 60 s), which is about holding locks rather than doing work.

The bundled Redis

It runs with a memory ceiling (redis.maxmemory, 768 MB) and noeviction. Without a ceiling Redis grows until the kernel kills it and every queued job goes with it. The usual allkeys-lru would be worse here than refusing: it would quietly evict queue entries and job records, so a query somebody submitted would simply never run and nothing would say so. Refusing is the honest failure — the enqueue reports an error and the person sees it.

It is replaced rather than rolled on upgrade. Two Redises behind one Service means the workers divide between two sets of queues, and a job enqueued through one is invisible to a worker reading the other.

Backups

Back up Postgres, and the uploads volume if people upload files — uploaded files live on disk, not in the database. Keep the semantic/ directory in git if you export the catalog. Redis holds queues, locks and a schema cache — losing it costs in-flight jobs and nothing else, which is why it can be a plain container with no persistence.

Restoring or moving the database needs the same SQLDESK_SECRET_KEY it was made with: data source and alert destination credentials are encrypted with it. To change the key, re-encrypt first rather than after:

manage database reencrypt <old key> <new key>
