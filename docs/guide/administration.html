Administration

Everything an administrator does, and where to look when something is wrong.

Users and groups

Groups carry permission. A user in the admin group can do everything; the default group is what everyone else starts in. Data sources are attached to groups, so adding somebody to a group is how they get access to data.

Users can be disabled rather than deleted, which keeps their queries and dashboards intact and attributed.

The Admin pages

Admin in the top row, for anyone with super_admin. Each page says what it is for in a line or two under its tabs, so you are not guessing which of seven holds the number you want.

Overview
Where the headroom is going: Postgres connections, Redis memory, how many workers are busy, how deep the queues are. Also who has run the most queries in the last hour and how much of that came from cache. The place to start when the instance feels slow and you do not yet know why.
System Status
The server's report on itself — version, uptime, when the query manager last made a pass, queue depths, table sizes. The figures to quote when something has to be escalated.
RQ Status
The job queues themselves, worker by worker. A queue growing while workers sit idle means the jobs are going somewhere nobody is listening.
Storage Status
What is being held and what happens to it when: cached query results, uploaded files, and how much of its quota each organisation has left. Both clean-ups can be started from here rather than waiting for their slot. See What happens to uploaded files.
Running Queries
Everything the workers have in flight, who asked for it, against which data source and for how long. A scheduled refresh shows as the scheduler rather than a person, because nobody is waiting for it. Any of them can be stopped from here, and stopping one is recorded.
Streaming Queries
Every Kafka topic being consumed, the rate events are arriving at, and — the column it exists for — why a quiet one is quiet. Paused, broken and genuinely empty look identical on a chart and are three different problems. The row budget and the events-per-second ceiling are set here. Shown when streams are on.
Outdated Queries
Scheduled queries whose next run is already overdue. A handful is ordinary; a long list means the workers are not keeping up with the schedules people have set.
MCP
Who has connected over MCP, what they asked for, and every refused attempt — never the question somebody put to their client and never the SQL that came back. A write records what it changed, before and after, because "update_table ok" does not answer the question anybody brings to an audit of an agent's writes. Shown when MCP is on. See MCP.

Reviewing what an agent wrote

An agent pointed at the catalog can describe a warehouse in an afternoon — that is the point of letting it — and that is also why a badge here and there among three thousand tables is not a review. Catalog has a Written by an agent filter that answers exactly that question, and each description carries the name on the API key that wrote it, not merely the fact that a machine did.

Two things an agent cannot do, deliberately:

  • Hide a table. It decides what everybody is offered, there is no review step, and nothing on a page would show it had happened. It is done here, with the table in front of you.
  • Agree a measure. A proposal lands under Measures with Agree and Deny; until somebody agrees it, no other agent is told it exists. A definition of revenue that is merely plausible is worse than none.

Every write is capped at fifty a day per person (SQLDESK_MCP_WRITES_PER_DAY). An agent told to describe a warehouse will describe the whole warehouse, and a loop getting it wrong will do it just as fast; fifty keeps a mistake to a morning's review rather than a restore.

Settings is its own menu in the top row rather than a gear on the right, and it holds different things for different people: an administrator sees data sources, users, groups, alert destinations and the organisation's settings; everybody else sees their snippets and their own account.

Permissions an administrator hands out

Some things are neither for everybody nor only for administrators. The person who knows what a table is for is rarely the person who runs the cluster, so these are granted to a group, under Settings → Groups, and anyone in that group has them.

What happens to uploaded files

An uploaded file is the only copy there is. A query result can be fetched from the warehouse again; a CSV somebody dragged in six months ago and has since deleted from their laptop cannot be re-created by anybody. So the policy is deliberately cautious, and nothing is ever deleted without a warning somebody could have acted on.

  1. Three days unqueried: unloaded. The file stops being registered with DuckDB, so queries on that data source no longer pay to infer its schema. The file is untouched and the next query that names it brings it back. Nobody is told, because nothing was lost.
  2. Six days: its uploader is emailed — one message, however many of their files are due, each with its size, whether it has ever been queried, and a button that keeps it.
  3. Seven days: deleted, but only files that were warned about. If mail was not working, nothing is deleted; the warning is retried instead. A file whose uploader has no address is never deleted on a timer at all — an administrator removes it from the Storage page, having looked at it.

Keeping a file is a permission (Keep uploaded files) an administrator grants to a group, from the email, the Storage page, or the data source's own page. A kept file stays until somebody deletes it.

The quota is a ceiling on everything uploaded, 5 GB by default. An upload past it is refused with the figures in the message, including how many files nothing has queried in a month — removing those is almost always the answer.

Turn any of it off with SQLDESK_UPLOAD_LIFETIME_DAYS=0, SQLDESK_UPLOAD_UNLOAD_AFTER_DAYS=0 or SQLDESK_UPLOAD_QUOTA_MB=0. The reason the default is not "keep everything" is that keeping everything is what SQLDesk did until 0.7, and on a development machine it filled the disk and took Postgres with it.

Keeping it healthy

  • Query results are the biggest thing in the database. A cleanup job removes results nothing points at; if the database is growing, check that it is running.
  • Dashboards stale? Look at Outdated Queries, then at worker count. Slow queries queueing behind each other is the usual cause.
  • Pages slow but data fresh? That is the web tier, not the workers.
  • Give a slow data source its own queue so one warehouse cannot starve the rest. On the data source’s page, under the extra fields: a Queue for the queries people are waiting for and a Scheduled queue for its refreshes — keeping those apart is what stops a refresh storm delaying somebody at a dashboard. Then run a worker whose QUEUES names them; a queue nothing serves is a data source whose queries wait forever, with nothing in any log to say why.

Streams, operationally

What a stream costs is different in kind from everything else here: a query costs when somebody runs it, and a stream costs continuously. So the two numbers worth knowing are the row budget (how much disk a stream may take) and the events-per-second ceiling (how much work it may make a worker do). Past the ceiling events are sampled rather than queued — an unbounded queue in front of a slow writer is the crash, not the protection against it.

A stream holds a worker while it is consuming, so give streams a queue of their own (SQLDESK_STREAM_QUEUE is not a setting yet — the jobs go on streams, and a worker whose QUEUES names it is what keeps a consumer out of the way of the queries people are waiting for). One worker per active stream, and only while somebody is watching: see a stream is a window.

Raw events live in a DuckDB file per stream, under the same volume as uploaded files — so the uploads volume is what fills if a budget is set too high. The per-minute rollups live in Postgres, because they are small by construction and are the part that has to survive a restart.
