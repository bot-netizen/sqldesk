Where the query path was wasting a second.

Four fixes to the caching layer, each one found by measuring rather than guessing. A 27MB cached result now serves in a tenth of the time, and the cache lookup behind it went from 66ms to 0.06ms.

One: the payload was decoded and re-encoded on every hit

Query results are stored in Postgres as JSON text. They leave over HTTP as JSON text. In between, the old path built the entire Python object graph and threw it away.

01

Splice the stored bytes instead of re-encoding them

Postgres TEXT ──▶ json_loads() ──▶ Python dicts ──▶ json_dumps() ──▶ HTTP
                   328 ms                            663 ms

Postgres TEXT ─────────────────────────────────────────────▶ HTTP
                   payload passes through untouched
Before547 msexcludes the decode already paid
After99 msincludes load and raw read
Saved82%per cache hit

The surprise was inside the encode. _sanitize_data, which walks the whole object graph looking for NaN and values JSON cannot represent, cost 291ms — more than the 252ms serializer it guards. It could never find anything: unrepresentable values fail at insert time, so on the read path it was pure overhead.

The metadata is still encoded normally, which is cheap because it is tiny. The payload is spliced into the slot it would have occupied, using a fresh random token per call rather than a fixed marker — so a payload cannot contain the string that would displace it, because it cannot know the token.

The decode is skipped too, by deferring the mapped column. Deferring is transparent, so the CSV and Excel paths that genuinely need decoded data trigger an ordinary lazy load and behave exactly as before.

Two: the cache lookup got slower the longer you used it

Checking for a cached result filters on three columns and sorts on a fourth. Only one of them was indexed.

02

A composite index matching the actual query

-- before: every row that ever shared the hash, then filter, then sort
Limit
  -> Sort  (Sort Key: retrieved_at DESC)
       -> Bitmap Heap Scan on query_results
            Recheck Cond: query_hash = ...
            Filter: data_source_id = ... AND retrieved_at + interval >= now()

-- after: one descent, no sort
Limit
  -> Index Scan using ix_query_results_cache_lookup
       Index Cond: query_hash = ... AND data_source_id = ...
Before66.7 ms3,356 buffers
After0.064 ms4 buffers
Faster~1000×on 100k rows of history

The cost was linear in how much history a query had accumulated — and a query refreshing every five minutes accumulates roughly 105,000 rows a year. The index is (query_hash, data_source_id, retrieved_at DESC), with retrieved_at descending so the first row the index yields is the answer and no sort is needed.

The old single-column index was dropped at the same time. Every query on this table that filters query_hash also filters data_source_id, so the composite's leading column covers it — and two indexes where one serves taxes every insert on the most-written table in the schema.

Built without locking

Both operations run CONCURRENTLY, so no write lock is held on a table that could hold millions of rows. Upgrade and downgrade were both exercised before shipping.

Three: old results could accumulate faster than they were deleted

03

Lift the eviction cap, and say when it binds

288 runs/day  ×  100 rows/run  =  28,800 rows/day maximum
                                 ≈ 20 results a minute

A few hundred queries on short schedules exceeds that, and past that point the table grows without bound — forever, with nothing saying so. The cap is now 1,000 per run.

The more useful change is the second one: the job now warns when it deletes its full quota. The failure mode was never the number, it was the silence. A disk filling up is a bad way to learn that cleanup has been losing a race for months.

Four: DuckDB reconnected on every query

04

Cache connections per process, and health-check them

DataSource.query_runner is a property, not a cached attribute — so every access built a new runner, which opened a new DuckDB connection and reran INSTALL and LOAD for each configured extension. Per query.

Connections are now cached per process, keyed by the configuration that produced them so two differently configured sources never share one. Each RQ worker is its own process, so the cache is naturally per-worker.

The part that needed care

A cached connection outlives any single query and can be invalidated underneath you — the database file replaced, say. Without a health check, one dead connection would fail every subsequent query in that process, which is strictly worse than not caching at all. So the cached connection is checked before reuse and transparently replaced if it has died.

How these were found

Every figure on this page came from running something on the actual stack — timing the serializer against a real 100,000-row result, and EXPLAIN ANALYZE against a table loaded with a year of realistic history. None of them are estimates.

That mattered more than once. An early version of the index looked like it changed nothing, because the test table had four rows in it and the planner was right to ignore an index at that size. The improvement only became visible — and only became real — once the table held the history a production instance would actually have.
