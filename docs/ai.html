AI, on what SQLDesk already knows

Four surfaces — an MCP server, an assistant, an optimize button and a semantic layer — are clients of one context service built from your warehouse and your own query history. Build the context service first; the rest are thin on top of it.

How it works All releases

The shape of it

Nothing but the context service touches raw schema. The MCP server is the single tool layer, and the in-app assistant is a second client of it rather than a parallel implementation — so retrieval, guards and permissions live in one place.

Every call executes as the signed-in user and honours the data source and group permissions that already exist. No service account with blanket access.

What arrives, in order

  1. The context service No AI

    Harvest each source on a schedule — partition specs, sort orders, column cardinality, null fractions, distribution keys. Ships on its own as much better schema search, and everything later depends on it. The eval set is written here too, before any retrieval work, or tuning happens by vibes.

  2. The optimize button, deterministic half No AI

    Beside Execute in the query editor. Parse, EXPLAIN, and rule packs per engine: missing partition predicate, an implicit cast killing partition pruning, SELECT * on a wide columnar table, ORDER BY without LIMIT. Needs neither the catalog nor a model, which is why it comes early.

  3. The MCP server

    Task-shaped tools, not CRUD-shaped. find_context(question) returns ranked tables with columns already pruned plus a few similar past queries — one call instead of the forty a list_tables / get_schema pair provokes. Runs against Claude Desktop immediately, which is how we find out whether the context is any good.

  4. The rewrite half of the optimizer

    A rewrite with a rationale per change, and then the part that matters: normalize and parse both, EXPLAIN both, run both against one partition and compare row counts and a sorted hash. Then label it honestly — verified equivalent on one day of data, or not verified, review manually.

  5. The assistant, and the semantic layer

    The assistant is a second client of the same tools. Every identifier it generates is checked against the catalog, so a hallucinated column fails closed rather than reaching the engine. Assumptions are always surfaced.

The semantic layer, and why it is not a modelling project

A metric definition is usually already written down — in a query somebody saved.

SELECT region, SUM(amount) AS revenue
FROM orders WHERE status = 'completed' GROUP BY 1

That is a measure, its name, its filter and its grain, written by a person who knew the business. No model is needed to name it. Parse, count how many people wrote it, and propose it.

Authored

Someone writes it. Works on day one, and is only as good as what they know.

Proposed from schema

Suggested at harvest time from names and types. Weak, but better than an empty page.

Inferred from queries

Strong, and compounds — worth nothing on day one and a great deal by month three.

Nothing a model proposed reaches a query until a person says yes. Proposals land in an approval page with their provenance — seen in 23 queries by 9 people — and an admin accepts, renames or rejects. Only approved definitions are used.

Approved definitions are written as Cube-native YAML, so they can live in git, be reviewed as a diff, and be absorbed by Cube without a conversion step. Our own compiler reads the same files, which means SQLDesk needs no extra service to use them — and cannot invent a feature Cube has no word for.

Your model, your hardware

Configured from the CLI on the server, because the people who run SQLDesk on their own machines are the ones who most need to choose.

sqldesk ai configure --provider anthropic --model claude-sonnet-5
sqldesk ai configure --provider openai    --model gpt-4.1
sqldesk ai configure --provider local     --base-url http://ollama:11434 --model llama3.1
sqldesk ai status

Off until it is configured. No key, no AI features, no outbound requests — and a per-data-source switch, so a warehouse holding anything sensitive never reaches a hosted model even when another one does.
