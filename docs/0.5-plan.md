# 0.5 plan

Work found while stabilising 0.4 and deliberately held back so the release
candidate stops moving. Each item carries the measurement that justifies it, so
nobody has to rediscover the problem before fixing it.

Numbers were taken on `release/0.4` at `b5de1c03` with throwaway probes. They
are reproducible: count SQL statements with a `before_cursor_execute` listener,
and time the browser side in a jest test. Re-measure rather than trusting these
after any of it changes.

## 1. One execution per query, per dashboard refresh — **done**

**The problem.** Every widget builds its own `Query` from
`visualization.query` in `client/app/services/widget.js`, so widgets that show
the same query share nothing. Probed with three widgets over one query:

- first load: three `GET /api/queries/7/results/99.json` — the same result id,
  fetched three times
- Refresh: three `POST /api/queries/7/results {max_age: 0}`

The database is usually spared, because `enqueue_query` holds a Redis lock on
`(data_source_id, query_hash)` and POSTs that overlap a job in flight get the
same job back — confirmed. What is paid every time is the result: three
downloads, three server-side serializations, and three runs of
`QueryResult.update()`.

That last one is the expensive part. On a 20k-row, 8-column result (3.3 MB):

| | |
|---|---|
| `JSON.parse` | 14 ms |
| `QueryResult.update()` | **960 ms**, on the main thread |

So three widgets on one query is about 2.9 seconds of blocking work on
identical data, and 10 MB transferred instead of 3.3.

**The fix.** Group widgets by query id, parameter values and auto-limit in
`loadDashboard`; run each group once and share the resulting `QueryResult`.
Contained to `useDashboard.loadDashboard` and `Widget.load`.

**Watch out for:** `getFilters()` caches onto the result object, so widgets
sharing one result would share filter state. Dashboard filters are already
collected globally, but widget-level filters need checking.

**Done**, though not where this said. Grouping inside `loadDashboard` would
have left the live path alone, and that is the worse case: the server names
one result id and every widget on that query fetches it separately. So the
sharing sits in the loading layer instead -- `services/inFlightResults` -- and
identical requests that overlap in time are answered once, whoever asked.
Every caller gets it, and `loadDashboard` and `useLiveDashboard` are unchanged.

The warning turned out not to hold: `getFilters()` builds a fresh array on
every call and caches nothing, and `VisualizationRenderer` keeps each widget's
filters in its own state. Nothing that renders a result mutates it.

Measured on a dashboard of five visualizations of one query, warm:

| | requests | transferred |
|---|---|---|
| before | 5 | 11.0 kB |
| after | **1** | **2.2 kB** |

## 2. Close the dedupe gap on the server — **done**

`_unlock` runs in `sqldesk/tasks/queries/execution.py` *before*
`store_result`. A sibling request arriving after the data comes back but
before the row is written starts a brand-new execution — confirmed with a
probe: three simultaneous POSTs returned one job id, and a POST issued after
`_unlock` returned a different one. Since widgets send `max_age: 0`, there is
no stored result to fall back on either.

Moving `_unlock` after `store_result` makes the window cover writing the
result, not just running it. Fast queries and big results are exactly the
cases that slip through today.

**Done.** The release moved into a `finally`, so a failed query still gives
the lock back -- that path stores nothing, and a lock left behind would hand
every later request a dead job id.

Do this together with item 1: the client stops asking twice, and the server
stops having a gap when something else does.

## 3. Index `query_results` for the lookup it actually does

`QueryResult.get_latest` filters on `query_hash` and `data_source`, then
orders by `retrieved_at desc`. `query_results` is indexed on `query_hash`
alone. A composite `(query_hash, data_source_id, retrieved_at desc)` turns the
filter-then-sort into a lookup. Needs a migration.

## 4. Stop turning every timestamp into a moment

Of the 960 ms above, `moment.utc()` on a single timestamp column accounts for
368 ms — 20k moment objects built eagerly, on the main thread, whether or not
the visualization needs them. `Date.parse` over the same column is 4.7 ms.

Bigger than it looks: viz-lib expects moments in places, so this needs a pass
over the consumers rather than a one-line change. Worth it — it is the single
largest cost in taking a result in.

## 5. A reading tile for the gauge

The dial spends a whole widget on one number and shows no history. Add a
fourth style — the value large and coloured by its threshold, a trail of the
last N points, and a bullet bar carrying the range, the bands and the target —
and make it what new gauges start on. The parts exist: the counter's sparkline
and the progress visualization's bullet mode. The only new option is a time
column for the trail.

Keep `needle` as the fallback for gauges saved without an explicit style, so
nothing existing changes appearance.

## 6. Lazy-load the visualization registry — **done**

`client/app/config/index.js` does a bare `import "@sqldesk/viz/lib"`, which
reaches a registry of sixteen static imports in
`viz-lib/src/visualizations/registeredVisualizations.ts`. An import-graph walk
from `viz-lib/src/index.ts` reaches **184 of its 229 files eagerly**, so every
page — the login page included — loads Leaflet, react-pivottable, d3-cloud,
moment and numeral. The careful ECharts budget in
`viz-lib/src/visualizations/echarts/index.ts`, which registers only the series
actually used, is undone by the registry around it.

The production bundle today: **5.42 MiB** for the app entry point — 4.27 MiB
of JavaScript and 1.42 MiB of CSS.

Registry entries hold `Renderer`/`Editor` function references and
`registerVisualization` only reads `config.type` eagerly, so `React.lazy` per
type is structurally straightforward. There is currently no code splitting in
the client at all — no `React.lazy`, no dynamic `import()` anywhere. This is
the biggest user-visible performance win available, and it is the thing to do
before adding tier 2 visualizations.

**Done.** The registry keeps a name, a size and `getOptions` — all cheap, all
synchronous, so `widget.js`, `VisualizationName` and the visualization editor
are untouched. The Renderer and the Editor moved behind a `load` that webpack
splits into a chunk per visualization, resolved through `React.lazy`.
Dashboards and query pages start those fetches as soon as they know which
types they hold, which is long before any result comes back, so the split
costs no visible pause. Entry JavaScript went from 4.27 MB to 2.86 MB, and a
dashboard with no map never fetches Leaflet.

## 7. One freshness policy

Nine client-side decision points compute or default `maxAge`, spread across
`useDashboard.js`, `widget.js`, `query.js` and `useLiveDashboard.js`, and
`undefined` means three different things depending on which one you are in:
"page load, reuse the cached result", "Refresh, run it", and "ignore me, I am
passing a result id". This has already produced two shipped bugs (`0230dcdd`,
`6385d6a3`).

Replace it with one function mapping intent — `page-load | refresh |
auto-refresh | live` — to `{maxAge, resultId, useCache}`, so callers name the
path rather than the number. Do this together with item 1; they are the same
problem seen from the client and the server.

## 8. Make the widget memo dependency honest

`DashboardGrid.jsx` passes a `queryResult` prop that nothing reads — it exists
only so `React.memo`'s comparator sees a change. One "remove unused prop"
cleanup reverts live dashboards to fetching but never drawing. The comparator
also omits `dashboard`, which changes identity on every `setDashboard`, so a
memoized widget holds a stale one — and that stale object is what
`editParameterMappings` hands to its dialog.

## 9. Take the rest of the live load off the request path

`_watch` refreshes synchronously inside the check-in request: parameter
rendering and a `get_latest` per widget before the viewer gets a reply. Move
it to a small job, or let the ten-second scheduler own it.

Alongside that: `latest_results` runs one `get_latest` per widget per viewer
per check-in with no dedupe by query hash, and `refresh_live_dashboards` scans
every dashboard with `live IS NOT NULL` every ten seconds, unpaginated and
with no overlap guard. It wants an index on that column and a Redis lock.

## 10. Retire numeral

Two number-formatting stacks ship side by side: `viz-lib/src/lib/value-format.tsx`
(numeral) for charts, table number columns, cohort, funnel, map and
choropleth, and `shared/valueOptions/format.ts` (Intl) for counter, gauge,
progress and status-grid. The same number can format differently in two
widgets on one dashboard. Numeral also formats by mutating a global locale,
which `counter/utils.ts` has to save and restore around every call — a latent
correctness bug if two things ever format concurrently.

This is a data migration, not a refactor: saved numeral format strings have to
be translated to the Intl `ValueFormat`. `counter/index.ts` is the model for
telling a new visualization from a saved one so existing ones are untouched.

## 11. Bring the stragglers onto the shared layer

- **The empty state exists three times.** gauge, progress and status-grid each
  implement `problem`, the message and the CSS separately, with identical
  strings. funnel, sunburst and sankey render a blank widget with no message
  at all. Three behaviours for one condition.
- **Funnel never joined 0.4.** `git diff v0.1.0..HEAD -- viz-lib/src/visualizations/funnel/`
  is empty. It still uses a hardcoded palette colour instead of semantic
  colours, numeral instead of the shared formatter, an antd table instead of a
  chart, and regenerates its React keys on every data change.
- **The font stacks are copy-pasted** between `gauge/buildOption.ts` and
  `progress/buildOption.ts`, in different orders — and `chart/echarts/buildOption.ts`
  sets no font at all, so charts render in ECharts' default sans-serif while
  the tiles beside them render in Instrument Sans. These belong next to
  `uiColor` in `shared/valueOptions/colors.ts`.
- **Gauge geometry is declared four times** in `gauge/buildOption.ts` — needle,
  ring/half, the target marker, and again as `radiusShare`. Changing a gauge's
  proportions means editing four places consistently.
- **`sanitize` and `resizeObserver` exist byte-identically** in both
  `client/app/services/` and `viz-lib/src/services/`. Both copies of `sanitize`
  call `DOMPurify.addHook` at module scope, so with hoisting the hook is
  registered twice on one singleton.

## 12. Skip off-screen widgets

Every chart on a long dashboard holds a live canvas and runs its enter
animation even when scrolled out of view. Tab visibility is handled
(`useLiveDashboard.js`), per-widget visibility is not. An `IntersectionObserver`
around `useEChart` would cost nothing and save a lot on a twenty-widget
dashboard.

## 13. Cover the gaps

- `useDashboard.js` has **no test file at all** — 341 lines, 27 hooks, a
  36-key return, and the hub of all four refresh paths.
- `widget.load()`'s `maxAge = force ? 0 : undefined` rule and its
  `this.queryResult === queryResult` identity guard are untested.
- Nothing asserts that an auto-refresh timer tick actually issues the max age
  it computed.
- viz-lib's own `type-check` is not part of `pnpm test`, so a type error there
  reaches CI only through the build.

## Decisions still open

- **Cron schedules cannot be set in the UI.** `CronScheduleDialog.jsx` and its
  LESS are unreachable, and `useSetQuerySchedule`'s `setCron` has no caller,
  but the backend validates and honours cron and the UI still reads existing
  cron schedules back. Either the wiring regressed or it was dropped on
  purpose; if the latter, those two files should go.
- `elliptic` is a declared runtime dependency that nothing imports — probably
  an old transitive-CVE pin that belongs in `pnpm.overrides`.
- `bootstrap`, `font-awesome` and `material-design-iconic-font` all ship
  alongside antd. Three CSS/icon frameworks is the largest remaining
  bundle-size target, but it needs a design pass, not a delete.
- The three unreachable SQL dialect formatters under
  `client/app/lib/sql-formatter/languages/` (Db2, N1ql, PlSql, 324 lines) are
  dead only because `queryFormat.ts` never passes a dialect. Prune the
  vendored library or leave it whole.

## Done in 0.5 so far

All on `release/0.5`. Frontend unless it says otherwise.

- **1. One fetch for one result, however many widgets want it.** See above.
  Five visualizations of one query: 5 requests and 11.0 kB, down to 1 and
  2.2 kB.
- **2. The query lock now covers writing the result** — backend. See above.
- **6. The registry stopped loading every visualization.** See above. Entry
  JavaScript 4.27 MB → 2.86 MB, with a chunk per visualization fetched on
  demand.
- **20. The eight tier-2 chart types.** Every chart on the roadmap's "more
  ways to read a result" is built: histogram, waterfall, radar, treemap,
  calendar heatmap, state timeline, plus the drawn funnel and the Nightingale
  rose, which are options on visualizations that already existed and default
  to what is already on people's dashboards. Each one keeps the part that can
  be got wrong invisibly — bin edges, running totals, hierarchy sums, day
  boundaries, span ends — in a module of its own, tested apart from the
  drawing. The two drawn with `renderItem` have their geometry measured
  against rendered SVG rather than assumed.
- **21. A one-off ECharts series travels with its own chart.** The shared
  ECharts chunk registers only what more than one visualization needs; radar,
  treemap, funnel and calendar register their own, so opening a bar chart
  does not download four series it will never use.
- **22. Every visualization put through every option it offers.** A matrix of
  data shapes against option variants, drawn for real and checked — the point
  being the options nobody clicks. It found two crashes of the same kind: a
  non-numeric column made the box plot push `null` into a series ECharts
  reads a field off, and the same again on the chart's box type. Both had an
  existing test pinning the broken behaviour, which is the argument for the
  matrix.
- **23. The editing guides show the grid the dashboard actually uses.** The
  overlay drew twelve columns and 50px rows against a grid that had been 24
  and 25 since item 17, so widgets snapped between the lines. It reads the
  real configuration now. The horizontal lines were missing too, and not for
  the reason it first looked: the mask that fades the guides out was a pixel
  out of phase and covered every row guide exactly.
- **24. A dashboard for a screen on the wall.** `/wall/dashboards/<token>`:
  dark, no chrome, type sized for four metres, and able to cycle through
  several dashboards on its own. The theme is a token override and nothing
  else, which is what makes it reach the charts — `uiColor()` reads the
  custom properties at the moment it draws. Every colour is measured against
  WCAG AA rather than chosen by eye, and the test checks the arithmetic.
  Cycling needed the api key to follow the dashboard: `/api/dashboards/public/
  <token>` answers with whatever the request's key points at, so asking for
  the next dashboard kept returning the current one — a 200, with the wrong
  body. A dashboard taller than the screen is walked down and back over its
  turn, because `overflow: hidden` on a display nobody is standing at does not
  hide the rest of a dashboard so much as lose it: 15 of 25 widgets, at
  1440x900. The status colours' background tints became tokens along the way —
  they were the one part of that system reading no token, so on a dark theme
  the ink followed and the tile did not, at 1.26:1.
- **25. A timer with nothing to count from no longer counts.** Every widget
  renders the refresh indicator all the time and CSS hides it, so 25 widgets
  meant 25 intervals a second formatting NaN into hidden spans, for as long
  as the page stayed open. Found on the wall display, which is a page that is
  never closed.

- **26. Dashboards are saved when you say so.** Dragging or resizing a widget
  wrote to the server about two seconds later, whatever you did next, so a
  dashboard was changed by anyone who opened it in edit mode and nudged
  something — Done Editing only left edit mode. That is upstream's behaviour
  and not a regression, but it is not what a button called Done Editing means.
  The arrangement is held now until it is saved, with Discard beside it and a
  warning before you leave. Deliberate divergence from upstream; do not
  restore the autosave.
- **27. One element can have more than one watcher.** `resizeObserver` kept a
  single callback per node and silently dropped the second, which is how a
  chart came to keep whatever size it was created at: drag a widget's edge and
  the tile resized while the chart inside it did not, and a chart created
  before the page had laid out stayed 0×0. Measured: a container 698px wide
  with a 0×0 canvas in it.
- **28. Sorting and searching on the list pages.** Rows and Runtime sort —
  both order on columns `all_queries()` already joins, so neither costs a
  round trip. The Filter field stopped eating what you type: it took its value
  from the list's debounced search term, so every keystroke was replaced by
  the older one and reappeared 200ms later.
- **29. An Admin section** — backend and frontend. The three admin pages
  existed and were reachable only through the profile menu, next to Log out.
  They get a tab of their own, plus an Overview that answers what an admin
  actually asks when the instance is slow: what is running (from the job
  queue, so it includes the scheduler), who is asking (from `events`, so it
  does not), what is about to run out (Postgres connections, both Redis
  servers, worker capacity), and what the big tables take. With actions: kill
  a running query, run the result cleanup now, prune `events`.

  `events` had no index but its primary key and gets a row per execution.
  Measured at 22,444 rows: the last-hour aggregation was a sequential scan,
  1,170 buffers, 26.9 ms; with `(org_id, action, created_at)` it is an index
  scan, 6 buffers, 0.134 ms.

  Three defects fixed in passing: `/api/jobs/<id>` had **no permission check
  on either method**, so any signed-in user could read or cancel anyone's
  running query from a job id; the RQ status page read the wrong Redis on any
  split-Redis setup; and `outdated_queries` 500'd on a fresh install.
- **30. A chart in the alert email** — backend, frontend and a new optional
  service. Up to five dashboards or queries, picked with a + button, arriving
  as images. The browser is **not** in our image: it is a separate optional
  container, the way Grafana does it, so the published image does not change
  size and an install that never turns this on pulls nothing. Compressed, we
  ship 525 MB against upstream Redash's 543 MB and Superset's 316 MB;
  bundling Chromium would have added ~400 MB to an image the server and the
  worker share.

  A picture is a nice-to-have and an alert is not, so every failure is caught
  and the alert goes out without it. Getting the picture to *look* like the
  page took three fixes that only a real send found: a dict where flask_mail
  wanted pairs (so it did not send at all), a capture taken before the charts
  had resized, and one taken mid-animation.

- **14. A description on a visualization** — still to do. `Visualization.description`
  is already a column, already serialized, and the API already accepts it; it
  has simply never been editable or displayed. A textarea beside the name in
  `EditVisualizationDialog`, and an info icon with a tooltip next to the title
  in `VisualizationWidgetHeader`, following the pattern the table column
  headers already use.
- **15. Charts got back the space reserved for nothing.** The top of a chart's
  grid held 24px on every chart, and nothing is ever drawn there — the legend
  goes right or below, never on top. Now 14, with the bottom at 10 when no
  legend or slider sits in it. A widget's own chrome was 106px of a 235px
  widget, so the header and footer gave a little back too. About a seventh
  more plot in the same box.
- **16. Y labels thin out only when they would crowd.** ECharts asks for five
  intervals whatever the height, so a two-row widget stacked six labels a
  dozen pixels apart. Now about one per 55px, capped at five — it only ever
  takes labels away, so anything tall enough is unchanged. `hideOverlap`
  alongside catches labels that are wide rather than numerous. The chart
  learned its own height from `shared/useElementSize`, which the gauge
  already used.
- **17. Twenty-four columns and 25px rows.** Twelve could do halves and
  quarters but not thirds. Everything that referred to the grid doubled with
  it, including the sizing each of the sixteen visualizations declares, and
  nothing changes size on screen — a widget with twice the rows on rows half
  as tall is the same pixels, and two new columns plus the gutter they no
  longer need equal one old column. Saved dashboards are re-seeded rather
  than migrated; there are no users yet, and doing this later would have
  meant rewriting everyone's layouts.
- **18. The loading screen shows our own logo.** It drew a CSS recreation of
  the Redash mark, credited to a repository of other companies' logos. It is
  the SQLDesk mark now, inline so it still needs no network round trip.
- **19. The dashboard filter toggle left its band.** One checkbox had a white
  strip across the whole dashboard to itself while editing. It sits beside
  Done Editing.

## Already done in 0.4

Kept here because the measurements belong together.

- **Dashboards load their widgets in one go.** Showing a dashboard walked
  every widget lazily — visualization, query, author, data source, groups —
  and re-read the viewer's permissions per widget. Twelve widgets cost 65
  statements; a live dashboard cost 74 per viewer per check-in, four times a
  minute each. Now 9 to show fifteen widgets and 19 to check in on them, and
  `tests/test_dashboard_load_cost.py` holds the shape: adding widgets must not
  add anything but their own result lookups.
- **`isDateTime` rules out non-dates by shape first.** A strict moment parse
  costs about fifty times the regex, and it ran on every string cell of every
  result — a quarter of the cell scan.
- **336 type suppressions went**, from fixing two declarations: `Section`
  intersected its props with `typeof defaults`, narrowing `children` to
  `null`, and `withControlLabel` returned an untyped wrapper so
  `Select.Option` did not exist to the compiler. viz-lib had 685; it has 349.
- **1,144 lines nothing reached were deleted** — eight LESS partials from the
  original theme including a Flot/sparkline stylesheet, a dead `UnicodeWriter`
  that would have raised `AttributeError` if anything had called it, an empty
  `google_spanner.py`, a superseded `lib/pagination`, two `ColumnEditor`
  shims, and the last Plotly references in `base.less` and `webpack.config.js`.
- **Counter reads its row through `shared/rows`**, which also fixed a crash:
  counting rows against a target with an empty result indexed into the empty
  array. `rowIndex` and `pickRow` now have tests.
- **`moment` and `lodash` are declared**, rather than resolving through
  `shamefully-hoist` and antd's own dependency.
- **Live dashboards stopped retrying a failing query every ten seconds.** A
  failed refresh stores no result, so the freshness check found nothing on
  every scheduler tick — roughly 30x the intended rate on a five-minute
  dashboard. Live now records that it asked, for as long as a result would
  have stayed fresh. That also closed the one way a viewer could ask the
  server to run something repeatedly: leaving and returning to a tab.
  Refreshes moved to the scheduled queue, without becoming scheduled queries,
  which would have mailed the query's owner on every failure.
- **A table data bar no longer collapses on refresh.** The bar measures itself
  against the cell, and it was being wrapped in the change highlight, which
  shrinks to fit the number — so from the first refresh its width was a
  percentage of the digits rather than the column.
