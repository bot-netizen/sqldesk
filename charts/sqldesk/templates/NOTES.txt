SQLDesk {{ .Values.image.tag | default .Chart.AppVersion }} is installing.

On a first install the tables are made by a job that runs alongside the
server, so the first page errors until that job completes -- usually a
minute. On an upgrade the job runs before anything changes.

  kubectl get pods -l app.kubernetes.io/instance={{ .Release.Name }} -w

{{- if eq .Values.service.type "NodePort" }}

Reaching it on minikube:

  minikube service {{ include "sqldesk.fullname" . }}{{ if .Release.Namespace }} -n {{ .Release.Namespace }}{{ end }}

or forward a port, which keeps the same address between restarts (8080
rather than 5000, which macOS keeps for AirPlay):

  kubectl port-forward svc/{{ include "sqldesk.fullname" . }} 8080:{{ .Values.service.port }}
  open http://localhost:8080

and install with `--set host=http://localhost:8080`, so links in emails
point there.
{{- else if .Values.ingress.enabled }}

Reaching it:

  http{{ if .Values.ingress.tls }}s{{ end }}://{{ .Values.ingress.host }}
{{- else }}

The service is ClusterIP, so reach it from inside the cluster or forward a port:

  kubectl port-forward svc/{{ include "sqldesk.fullname" . }} 8080:{{ .Values.service.port }}
{{- end }}

First run: open that address. The first page asks for an organization name
and your details, and makes you its administrator. It is there until
somebody fills it in, so do that before telling anyone else the address.

{{ if .Values.mcp.enabled -}}
MCP is on. Its endpoint is /mcp, authenticated with the API key from your
profile page, and the audit is under Admin -> MCP. The catalog it answers
from is rebuilt every {{ .Values.mcp.catalog.harvestHours }} hours; to fill it now, after adding a
data source:

  kubectl exec deploy/{{ include "sqldesk.fullname" . }}-server -- ./manage.py ai harvest

{{ if and .Values.mcp.enabled .Values.mcp.queue .Values.mcp.worker.enabled -}}
MCP queries go on the {{ .Values.mcp.queue | quote }} queue, served by
{{ include "sqldesk.fullname" . }}-mcp-worker and nothing else, so a model
exploring cannot slow down a dashboard somebody is watching.
{{- else if .Values.mcp.enabled -}}
MCP queries share the data source's ordinary queue, so they compete with
dashboards for workers. Set `mcp.queue` and `mcp.worker.enabled` to give
them their own.
{{- end }}

{{ if eq .Values.service.type "NodePort" -}}
NodePort carries the API key in the clear. Fine on minikube, not off it --
put an Ingress in front and terminate TLS there.
{{- end }}
{{- else -}}
MCP is off. Turn it on with `--set mcp.enabled=true` and see
https://bot-netizen.github.io/sqldesk/guide/mcp.html
{{- end }}

{{- if not .Values.host }}

WARNING: `host` is unset, so links in emails and alerts will point at
localhost. Set it to the address people actually use.
{{- end }}

{{- if .Values.rendering.enabled }}

Alert emails can carry pictures: the renderer runs as
{{ include "sqldesk.fullname" . }}-screenshots, and an alert's edit page has an
"Attach" row for the dashboards and queries to include.
{{- end }}

{{- if and .Values.uploads.enabled (eq .Values.uploads.accessMode "ReadWriteOnce") }}

Uploaded files live on a ReadWriteOnce volume, so the workers run on the
server's node. With a ReadWriteMany storage class, set
`uploads.accessMode=ReadWriteMany` and they can go anywhere.
{{- end }}

{{- if and .Values.postgres.enabled (not .Values.postgres.external) }}

NOTE: this installed a Postgres for you, which is meant for development. For
anything you care about, point `postgres.external` at a managed database and
set `postgres.enabled=false`.
{{- end }}
