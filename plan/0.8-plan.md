# SQLDesk 0.8.0 — Notebooks

Scope agreed with Iqbal on **2026-10-03**. Not started.

Everything in 0.8 points one way: **you should know what a thing costs before
it runs.** 0.7 made the heavy parts optional so an install pays nothing for
what it does not use; 0.8 does the same for a single query.

## The headline: notebooks

Everything in SQLDesk today ends in one SELECT. A notebook is for the work
that does not: pull this, join it to that, reshape it, look, then write the
result somewhere. People do that in Jupyter today and the warehouse never
hears about it — so the lineage, the permissions and the scheduling all stop
at the edge of somebody's laptop.

- Cells in **SQL and in Python**, each reading the last one's result, saved
  and re-runnable.
- Any cell's output available as a visualization or a dashboard widget.
- The parts SQLDesk already has — data source permissions, parameters, the
  scheduler, the result store — are most of what a notebook needs. What it
  adds is the chain.

Shape designed in [0.8-notebooks.md](0.8-notebooks.md) — the product
argument, the execution boundary, and the four decisions still open.
`CronScheduleDialog` was kept on purpose for this; do not delete it as dead
code.

## A streaming widget says what it is doing

Asked for on 2026-10-03, while deciding the nav restructure.

The stream editor tells you everything you need to believe an answer: the
rate, how much history the window holds, whether it is sampled and at what
share, how long it has been running, how many people are watching, and why a
quiet topic is quiet. A widget on a streaming dashboard tells you none of it.

The mismatch is structural, and it is the part to design carefully: **the
refresh is per dashboard, the events are per widget.** One board can hold
widgets over three different topics, each arriving at its own rate, any one of
which can be paused, sampled, or empty while the other two are fine. A single
"● Live · every 2 seconds" badge on the header describes the redraw, not the
data, so a chart that stopped moving twenty minutes ago looks identical to one
that is keeping up.

What it needs: the editor's metadata, per widget, small enough to live in a
widget's corner — and a dashboard-level roll-up that is honest when its
widgets disagree ("2 of 3 streams consuming"). The numbers already exist on
`api/streams/running`; what is missing is carrying them to the widget and a
design that does not turn every panel into a status board.

## An archived-dashboards list

There is an `is_archived` flag and an Archive action, and no way to see what
has been archived: no list, no endpoint, no sidebar entry. An archived
dashboard is reachable only by its URL. Queries have had `/queries/archive`
since the fork; dashboards never got the matching half. Scoped out of the 0.7
nav work once the dropdowns stopped enumerating views — see
[0.7-nav.md](0.7-nav.md).

## A cost model, before the query runs

Bytes scanned and an estimate of the work, from the engine's own planner,
shown as a number a person can refuse. MCP already refuses past a ceiling
(`SQLDESK_MCP_MAX_QUERY_COST`); this makes the ceiling visible rather than
something you discover by hitting it.

## MCP asks before it spends

An agent exploring should not quietly run a 4 TB scan because it seemed like a
reasonable next step. Past a threshold the tool returns the estimate and waits
for a person to say yes. Iqbal's words: *"every MCP ask should analyze and ask
user if he is okay with cost if it is crazy high."*

## An audit an administrator can read

Every execution is already recorded in `events`; nothing reads it as a
history. With it: who has been expensive this month, not just this hour.
Explicitly asked for on 2026-10-03.

## Query pools: a cap on the resource, not on the workers

Agreed with Iqbal on **2026-10-29**: *"we should do a per data source cap as
well irrespective of workers we have."* That last clause is the requirement,
not a detail of how it is built.

Today concurrency is a side effect of deployment. `WORKERS_COUNT` processes
times however many replicas are running is how many queries execute at once,
and the only way to change it is to change the deployment. One person can
still queue fifty queries against the shared warehouse, and nothing anywhere
says no.

### The unit is a named pool, and a data source points at one

SQLDesk is not what falls over. The warehouse is -- its connection limit, its
concurrency slots, its credits -- so that is what the budget belongs to. A cap
on SQLDesk as a whole would be the same number for a Postgres toy and a
Snowflake bill, which is a number that is wrong twice.

The first draft of this keyed the budget to the data source and Iqbal asked
why not a top-level pool, the way Airflow does it. He was right, and the
reason is one case the per-source version cannot express at all: **two data
sources on one warehouse.** `prod-readonly` and `prod-analytics` are separate
rows here, different credentials, the same machine. Cap each at eight and the
machine is handed sixteen.

So a pool is a **named** thing and a data source names the pool it draws from.
Every data source gets one created for it, so the default behaviour is the
per-source cap with nothing to configure; pointing two sources at one pool is
then a matter of typing the same name. A pool need not be a database at all --
a rate-limited HTTP connector is the same kind of scarce.

This costs nothing over keying by data source: the Redis key is a string
either way.

### A heavy query takes more than one slot

Airflow's second idea is worth more than its first. A task declares how many
slots it needs, not just that it needs one -- and that is the hinge that joins
this to the cost model above.

A query the planner estimates at four terabytes and one at four gigabytes are
not the same load, and counting both as "one query" makes a cap that is either
far too loose or far too tight. Weight a request by its estimate and the
budget stops measuring concurrency and starts measuring load, which is what
the warehouse actually feels.

Until the cost model lands, every query weighs one, and the two features ship
in whichever order suits.

**And it must hold whatever the worker topology is.** Four processes on one
node, or forty across twelve, or an HPA moving between them while a query
runs: the warehouse sees the same ceiling. That rules out expressing this with
queues and worker counts, because those *are* the topology. It belongs in
Redis, which every worker already shares, checked at the moment work is
handed out.

**What not to copy from Airflow.** It enforces pools in the scheduler, a
single process deciding what may run. There is no such dispatcher here, and
`scale.md` already lists the scheduler as a singleton with no leader election;
a second one would be a liability, not a feature. Acquire in the worker at the
moment work begins, as the streaming slots already do.

And keep the floors below. Airflow has `priority_weight`, which breaks ties --
it is not a guarantee, and at equal weight an agent still starves people. A
floor is a promise a priority cannot make.

The streaming slots are the proof that this works. `sqldesk/streams/slots.py`
holds a hash under a short lock, renews while the work runs, and lets the
entry expire on its own -- so a killed worker, a drained node or a closed
laptop all end the same way, with the slot free shortly after. Nothing depends
on a worker surviving long enough to give it back. Generalise that module
rather than writing a second one.

### Features divide the budget: a floor, a ceiling, and borrowing

Within a data source's budget, each feature gets a reserved floor and a
ceiling it may not pass.

| Feature | Floor | Ceiling |
|---|---|---|
| Interactive -- ad-hoc and dashboards | 50% | 100% |
| Scheduled refresh | 25% | 50% |
| Alerts | 10% | 25% |
| Notebooks | 10% | 50% |
| MCP and other agents | **0%** | 25% |

Both halves are load-bearing. Floors without borrowing waste the warehouse: a
reserved slot nobody is using is money burning. Borrowing without floors lets
whatever is busiest take everything, and the dashboard somebody is presenting
from stalls behind a refresh storm.

**MCP's floor of zero is the point of the whole table.** An agent may use
capacity that is idle and may never take the last slot. That is a sentence
with no encoding in a queue, and it is the rule that matters more every month.

### A refusal must not hold a worker

The trap in any semaphore is a worker blocking on it: a process waiting for a
slot is a process not doing other work, and a concurrency cap that causes
head-of-line blocking makes throughput worse than no cap at all.

So a refusal re-enqueues -- jitter, a bounded number of attempts, and the
worker goes straight back to the pool. An interactive query says "waiting for
a slot on <source>" rather than spinning in silence, and MCP refuses with a
sentence the way it already refuses on cost.

### The kill switch is the same feature

A pool whose budget is zero accepts no new work and keeps everything
else: its queries, its dashboards, its schema, its permissions. That was
listed here as a second item and it is not one -- it is this item with a
number set to zero.

### Shipping it

1. **Pools and a cap, no feature split and every query weighing one.** The
   smallest thing that stops the fifty-query stampede: a pool per data source
   created by default, and one `acquire` inside `enqueue_query`.
2. **Feature floors and ceilings.** `enqueue_query(query, data_source,
   user_id, is_api_key, scheduled_query, ...)` already carries everything
   needed to label the request, so no caller changes.
3. **Somewhere to see it**: "3 of 8 slots on Warehouse", and the per-source
   budget on the data source page.
4. **Budget zero**, which is the kill switch, and costs nothing once 1 is
   done.

What already helps: `enqueue_query` dedupes on `(query_hash,
data_source_id)`, so fifteen widgets of one query are already one execution.
Slots sit on top of that and bound distinct work, which is the right thing to
bound.

## Prometheus metrics

StatsD is what SQLDesk emits, which is the wrong shape for most clusters now.
Queue depth, worker saturation and connection-pool use are the three that
matter. See [scale.md](scale.md).

## Cube: proven meaning moves out

Designed in `docs/0.7-plan.md` §7 and deliberately deferred. A measure that
has been agreed and used belongs in a semantic layer other tools can read, not
only in SQLDesk's. Three parts: an export a real Cube loads, asking rather
than guessing, and answering from Cube first where Cube already knows.

## Not in 0.8

Anything that would make SQLDesk call a model itself. MCP serves tools to a
client the user brings, and that stays true.
