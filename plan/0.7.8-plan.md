was wrong and what was missing, worked through in order.

## 7: there is no page-load regression, and here is why

Worth writing down because the answer is "nothing", and the next person to feel
it slow will want to know what has already been ruled out.

**The bundle is not it.** `client/bundle-budget.js` measures what the `app`
entrypoint needs, gzipped, and CI fails a build that exceeds
`client/bundle-budget.json`. Measured during this work: **528 KB against a
budget of 560**. The budget has not moved since September, when it was
recorded at 522 KB — so 0.7.7 added about **6 KB**, and could not have added
more without failing its own build.

**Chunking did not change.** `webpack.config.js` is byte-identical between
`v0.7.6` and `v0.7.7`. Per-visualization CSS chunks are older than both; the
`viz-counter.*.css` in the report existed in 0.7.6 too. `client/app/pages/index.js`
is also identical, so no page moved between the eager and lazy sets.

**Assets are served compressed, and fast.** From inside the server pod, with a
browser's `Accept-Encoding: br, gzip, deflate`, the whole initial payload is
**0.50 MB in about 44 ms**. Through a `kubectl port-forward` it is **52 ms wall
clock** for all four assets in parallel, so the forward is not the bottleneck
either.

> **The trap.** Probing with `Accept-Encoding: gzip` alone reports 2.38 MB and
> `Content-Encoding: none`, which looks exactly like compression being broken.
> It is not. flask-compress only uses an algorithm it can compress
> incrementally on a *streamed* response, and its streaming set is
> `('zstd', 'br', 'deflate')` — **gzip is not in it**. A static file is
> streamed. `sqldesk/compression.py` says so in its docstring; this was still
> measured wrongly first.

**The request path got faster, not slower.** `handlers/base.py` gained
`record_events`, which batches a page's events into one job — about 75 jobs for
75 small inserts on a thirty-widget dashboard before.

**The install is healthy.** All seven queues empty, the 0.7.7 `periodicWorker`
running. Server-side request timings from real traffic: median **41 ms**, and
`/api/dashboards/36` at **41.5 ms** with 12 SQL queries. (`duration` in the
metrics log is **milliseconds** — `(time.time() - g.start_time) * 1000`.)

So what was most likely felt: the `ChunkLoadError` in the same report. A deploy
renames every chunk, and a tab open across one refetches everything and then
reloads itself. That is a genuinely slow load, once, and it is the only thing in
the console that was real.

One thing that is new and does cost something: `usePolledData`, added in 0.7.7,
polls on three admin pages (Overview, System Status, Running Queries). It skips
a turn while a request is in flight and rests in a hidden tab, so it is not a
leak — but those pages are busier than they were.

## 12: the bug under the bug

Search on the queries and dashboards lists was a text field inside an antd
Dropdown behind a button marked "Filter". It worked; nobody found it.

Underneath that, **searching any list fetched whole did nothing at all** —
alerts, groups, group members, outdated queries. `updateSearch` reports
`{ search: true }` and `PlainListFetcher.fetch` only went back to the server for
`tags` or `sorting`, so the term was dropped and the same unfiltered items were
re-paged. The comment above that condition read "only if tags or search
changes": the intent was written down and the code never matched it.
