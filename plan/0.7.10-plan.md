# 0.7.10

**Alerts over MCP is built** (28 Oct): `find_alerts`, `explain_alert` and
`save_alert`. What is left is the multi-panel chart, and a fix that missed
0.7.9 by a day.

## The table header, which 0.7.9 did not actually fix

0.7.9 removed the header fill in two places and the header stayed cream,
because a third rule painted it: the sticky-header rule in the table
visualization took `--color-surface-sunken`, with `!important`, so nothing
the variables said could reach it.

Fixed here, with a test that reads the stylesheet and asserts what paints the
header. The reason it shipped broken is worth keeping: it was verified on a
rendered specimen, and a specimen has nothing to scroll, so it has no sticky
header and the rule never applied. A specimen proves what it draws, not what
it leaves out.

## Alerts over MCP

**Asked for on 2026-10-27: "can we access alerts from MCP, like if I ask Claude
to debug an alert".** Until this, the answer was no. The fifteen tools covered
the catalog, saved queries, dashboards and running SQL; the word "alert"
appeared in
`sqldesk/mcp/__init__.py` only in two comments explaining why a published query
cannot be edited.

So an agent asked to debug an alert can at best guess which query is behind it
from the name, run that query, and report the current value. It cannot see the
threshold, the operator, the state, the destinations, or whether somebody muted
it a fortnight ago.

### Why now rather than earlier

Debugging an alert is almost always one of four questions, and 0.7.9 is what
makes three of them answerable:

| Question | What answers it |
|---|---|
| Why did this fire? | The threshold and the operator, with the value from `alert_fires` |
| Is it flapping? | The history — four fires and four recoveries in an hour reads instantly |
| Why did it *not* fire? | The current value against the threshold, plus `rearm` and `muted` |
| Was anybody told? | `alert_fires.notified` |

Before the fire history landed, a `find_alerts` tool could have said "it is
triggered" and almost nothing else. That is the kind of tool that costs context
and earns none back.

### The shape, as built

**`find_alerts(question)`** — matched by the alert's name and by the query's,
because alerts are usually named for the threshold while the subject somebody
asks about is in the query. Each line carries the condition as words
(`orders < 100`), the state, the fire count for the last 24 hours, and MUTED
where it applies.

**`explain_alert(id)`** — the condition, the value the query last returned and
when, the recent history with the value on each line and whether anybody was
told, and the destinations.

**`save_alert(query_id, column, op, value, name)`** — added after the read
pair, from "can we add a build alert option as well". Muted, with nobody
subscribed: an alert is not a draft, because it starts evaluating at once and
one with a destination starts waking people. Muted is the same shape as a
draft in the vocabulary alerts already have, and it buys a threshold trial
run — leave it muted a day and `explain_alert` says how often it would have
fired.

Both refusals it carries are about alerts that look like they work: a column
the query does not return, and a query that has never run.

### Size

Comparable to `save_visualization`: a day with tests. The permission model is
already there and the data is already there; what is new is two tools and their
refusals.

## Still open, carried forward

- **`save_visualization`'s schema is 336 tokens**, the heaviest of the fifteen,
  because it carries nine properties and two enums. Only an admin key pays it.
  Trimmable, but the enums are what stop a model inventing a chart type.
- **A screenshot tool for MCP.** `screenshots.capture(kind, obj, viewer, fmt)`
  already renders a dashboard or query to PNG or PDF, permission-checked
  against a viewer. What stops it being a tool is that images are expensive in
  context and `capture` returns `None` for every kind of failure, where a tool
  needs to say which. Worth having for "attach this to a ticket", not for
  "show me this dashboard" — `find_dashboards` answers that for a fraction of
  the cost.

## Visualizations

**Asked for on 2026-10-28, with a picture of what the hard one looks like.**
Four of the seven shipped in 0.7.9 the same day: the per-series line type,
the table header, the data bars, and the dashboard image that refused at
thirteen widgets. What is left is the part that is a feature rather than a
fix.

### A chart like the picture

The picture is three panels sharing one x-axis: spend over time with a dashed
day-ago and a dotted week-ago, a diverging bar panel of percent against the
same bucket a week back, and a two-line panel of deal against open eCPM.
Dashed comparison series, one legend, one time cursor.

The dash patterns landed in 0.7.9, so half of what makes that picture
readable is already there. What is missing is the panels.

**Redash's answer was custom Plotly JS**, a textarea behind
`allowCustomJSVisualizations`. That is not switchable back on here: nothing of
it survives the fork, and SQLDesk draws on ECharts, not Plotly. Rebuilding it
means user-authored JavaScript running in every viewer's browser -- which is
why Redash gated it behind a server flag in the first place.

**The declarative answer is better and gets the same picture.** ECharts lays
out stacked panels from a `grid` array natively. A chart that takes *n*
panels, each with its own series and y-axis, sharing the x-axis and the
tooltip, draws that image with no user JS to review and no hole to gate. It
composes with thresholds, palettes and the dash work; custom code composes
with nothing.

Custom JS stays available as the escape hatch if somebody wants the thing no
option covers. It should not be the first answer.

### MCP's share of this

`save_visualization` writes `chart | table | counter`, and for a chart
`column, bar, line, area, pie, scatter`. The editor already offers `bubble`,
`heatmap` and `box` on top of those; nineteen other registered types cannot be
created at all. Reading is fine -- `_chart_summary` names any type.

The three missing chart types are nearly free, since the option shape is the
one already there. The nineteen are not: each carries its own options, and the
schema is already the heaviest of the tools at 336 tokens. Widen the chart
enum; take the rest by demand, not by inventory.

### Shipped in 0.7.9

- **Line type per series.** Six patterns rather than ECharts' three, because
  its built-in dash lengths scale with the stroke and its dotted closes up at
  the 2px a chart line is drawn at.
- **The table header.** The fill measured 1.10:1 and the ink 3.33:1. Both
  gone: weight and a rule instead.
- **Data bars.** The negative bar's default colour did not exist, so the
  browser discarded the declaration and the bar had no fill. Solid bars now,
  with the number restated over the bar in a measured ink, a bars-only mode
  and a column width.
- **The dashboard image.** The PDF's one-page rule was being applied to the
  picture, which has no pages.
