# 0.7.10

Not started. The one thing agreed so far.

## Alerts over MCP

**Asked for on 2026-10-27: "can we access alerts from MCP, like if I ask Claude
to debug an alert".** Today the answer is no. The fifteen tools cover the
catalog, saved queries, dashboards and running SQL; the word "alert" appears in
`sqldesk/mcp/__init__.py` only in two comments explaining why a published query
cannot be edited.

So an agent asked to debug an alert can at best guess which query is behind it
from the name, run that query, and report the current value. It cannot see the
threshold, the operator, the state, the destinations, or whether somebody muted
it a fortnight ago.

### Why now rather than earlier

Debugging an alert is almost always one of four questions, and 0.7.9 is what
makes three of them answerable:

| Question | What answers it |
|---|---|
| Why did this fire? | The threshold and the operator, with the value from `alert_fires` |
| Is it flapping? | The history — four fires and four recoveries in an hour reads instantly |
| Why did it *not* fire? | The current value against the threshold, plus `rearm` and `muted` |
| Was anybody told? | `alert_fires.notified` |

Before the fire history landed, a `find_alerts` tool could have said "it is
triggered" and almost nothing else. That is the kind of tool that costs context
and earns none back.

### The shape

**`find_alerts(question)`** — the same shape as `find_queries` and
`find_dashboards`. Matched by name, returning the state, the condition in words
(`orders.count < 100` rather than three option keys), when it last fired, how
many times in the last 24 hours, and whether it is muted.

**`explain_alert(id)`** — the debugging one. The condition, the current value
from the query's last run, the recent history with the value on each line, and
where it notifies. Enough for a model to say *"it fired at 412 against a
threshold of 400 at 09:14, recovered at 09:20, and has done that four times
since midnight — the threshold is too tight"* without somebody reading two
pages to get there.

Both read-only, so they join the nine that need no write permission. Gated on
the same data-source access as everything else: an alert sits on a query, and
somebody who cannot read the query has no business seeing the alert on it.

### Two things to get right

**Cap the history.** The lesson from 0.7.7's token work: twenty lines at one
line each, not every row the table holds. An alert that has flapped for a month
should not be able to fill a context window.

**Refuse a stale answer rather than giving a wrong one.** "The current value"
taken from a query result three days old is worse than saying the query has not
run recently — the same instinct as the catalog saying when it has gone stale.

### Size

Comparable to `save_visualization`: a day with tests. The permission model is
already there and the data is already there; what is new is two tools and their
refusals.

## Still open, carried forward

- **`save_visualization`'s schema is 336 tokens**, the heaviest of the fifteen,
  because it carries nine properties and two enums. Only an admin key pays it.
  Trimmable, but the enums are what stop a model inventing a chart type.
- **A screenshot tool for MCP.** `screenshots.capture(kind, obj, viewer, fmt)`
  already renders a dashboard or query to PNG or PDF, permission-checked
  against a viewer. What stops it being a tool is that images are expensive in
  context and `capture` returns `None` for every kind of failure, where a tool
  needs to say which. Worth having for "attach this to a ticket", not for
  "show me this dashboard" — `find_dashboards` answers that for a fraction of
  the cost.

## Visualizations

**Asked for on 2026-10-28, with a picture of what the hard one looks like.**
Seven items, and they are not one size: three are an afternoon, two are a day,
and two are features.

### The small ones

**Line type per series.** `SeriesSettings` offers a name, a y-axis, a type and
an order. There is no dash. ECharts carries `lineStyle.type` per series
already, so this is one column in the editor and one pass-through in
`buildOption` — and it is what makes a comparison series readable: the same
colour solid for today and dashed for a week ago says "these are the same
measure" in a way two colours never do. Line and area both.

**The table header is cream, not grey.** `@table-header-bg: @n-100`, which is
`#f6f4f1` — red five points above blue, and that warmth is the cream. Wanted a
shade darker and neutral.

*The decision:* that token is every antd table in the application, not just the
table visualization. Changing it only in `viz-lib/src/visualizations/table/`
makes a result table differ from the lists around it. Change the token.

**Attachments, 5 to 20.** Worth naming the mismatch first: a dashboard
screenshot is already one picture of the whole dashboard and caps no widgets.
What is capped is `MAX_ALERT_ATTACHMENTS = 5`, how many dashboards or queries
one alert carries.

`screenshots.py` argues against raising it in its own docstring, and the
argument is still right: twenty captures in series is minutes, and every one of
those minutes is a threshold breach nobody has heard about yet. So raise the
cap *and* give `for_alert` a wall-clock budget — send what was captured when
the budget runs out, name the rest in the body. The rule the file already
holds: a picture is a nice-to-have and an alert is not.

### Data bars that can actually be seen

`washColor` returns a 16% mix, so every bar is a wash by construction, and the
negative one looks weakest of all because red reads lighter than blue at the
same alpha. The background fill has the same cause, running 6% to 46%.

Four things, and they are one feature because each is useless without the rest:

- **A solid fill**, not only the wash. The wash is right behind text; a bar
  read as a bar wants the colour it was given.
- **Text in a contrasting colour**, computed from the fill rather than chosen,
  so a dark bar takes white text and a light one black. This is what makes a
  solid fill safe to offer at all.
- **Bar only**, hiding the number, for a column read as a shape.
- **A width control**, because a bar in a narrow column says nothing.

Same treatment for the background fill, where the ceiling is 46% for the same
reason and has the same answer.

### A chart like the picture

The picture is three panels sharing one x-axis: spend over time with a dashed
day-ago and dotted week-ago, a diverging bar panel of percent against the same
bucket a week back, and a two-line panel of deal against open eCPM. Dashed
comparison series, one legend, one time cursor.

**Redash's answer was custom Plotly JS**, a textarea behind
`allowCustomJSVisualizations`. That is not switchable back on here: nothing of
it survives the fork, and SQLDesk draws on ECharts, not Plotly. Rebuilding it
means user-authored JavaScript running in every viewer's browser — which is why
Redash gated it behind a server flag in the first place.

**The declarative answer is better and gets the same picture.** ECharts lays
out stacked panels from a `grid` array natively. A chart that takes *n* panels,
each with its own series and y-axis, sharing the x-axis and the tooltip, draws
that image with no user JS to review and no hole to gate. It composes with
thresholds, palettes and the dash work above; custom code composes with
nothing.

Custom JS stays available as the escape hatch if somebody wants the thing no
option covers. It should not be the first answer.

### MCP's share of this

`save_visualization` writes `chart | table | counter`, and for a chart
`column, bar, line, area, pie, scatter`. The editor already offers `bubble`,
`heatmap` and `box` on top of those; nineteen other registered types cannot be
created at all. Reading is fine — `_chart_summary` names any type.

The three missing chart types are nearly free, since the option shape is the
one already there. The nineteen are not: each carries its own options, and the
schema is already the heaviest of the tools at 336 tokens. Widen the chart
enum; take the rest by demand, not by inventory.
