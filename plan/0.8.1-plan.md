# SQLDesk 0.8.1 — Notebooks people can live in

0.8 shipped the engine: cells, the handoff, staleness, Python in a container
of its own. 0.8.1 is the part that decides whether anybody uses it — asked for
on 2026-10-31, from opening 0.8 and trying to work in it.

The reference is explicit: **a mix of Zeppelin and Jupyter.** Zeppelin for the
notebook-as-a-document shape (a table of contents, per-cell controls, collapse,
run the whole thing, schedule it, publish it). Jupyter for the Python feel.
Where the two disagree, Zeppelin wins — this is a BI tool, not a laptop REPL.

## Running and scheduling

**Run all, from the top.** One button, running the chain in order. The engine
already knows the order and already refuses a cell that cannot run; what is
missing is the single action over the lot, and somewhere to watch it get
there.

**A schedule, like a cron.** When should this notebook run on its own. This is
what turns a notebook from a thing somebody opens into a thing that happens —
and it is the half that makes the next item worth anything.

## ETL, which is what a schedule is for

**Download a cell's output.** People will use this to move data, not only to
look at it. A cell that produced a table should hand it over — CSV, and the
format the handoff already is.

Together with the schedule this is a small ETL tool: pull, reshape, write out,
every morning. That is the use we are aiming at, so the download cannot be an
afterthought bolted to one cell type.

## Telling a cell what it runs on

**Python or a data source, chosen clearly.** Today the dropdown is data
sources, and the cell kind is decided elsewhere. A cluster is a third thing
again. The rule to make visible: **if a cell is pointed at a cluster it does
not need a data source**, and the page should make that obvious rather than
leaving two controls that look like they both apply.

Probably a separate control for the cluster, or a single "what does this cell
run on" selector with the three kinds grouped. Decide by drawing it.

## The document around the cells

**A left sidebar, as a table of contents.** Click a cell, jump to it. This is
the thing that makes a notebook of thirty cells navigable and the single
biggest reason Zeppelin notebooks are readable and ours is not.

**A title per cell**, defined by whoever wrote it, shown in that sidebar. A
sidebar listing `cell_1 … cell_30` is a sidebar nobody reads.

**Collapse a cell**, and collapse a notebook's sections. Long notebooks are the
normal case, not the edge.

**Per-cell buttons, the way Zeppelin has them:** run, show/hide the code,
show/hide the output. Three separate toggles, because reading a finished
notebook and writing one want opposite things on screen.

**Space between the code and the output.** They currently run together and the
eye cannot find the seam.

**The notebook header should match the table header**, so the page looks like
the rest of the product rather than like a page somebody added later.

**Counts on the notebook and on the list:** how many data sources it touches
and how many cells it has. On the notebook page and on the notebooks list, so
the list says something before you open anything.

## Saying what this is for

**Two or three lines, on the page**, on why a notebook is not a query and not
a dashboard. People arriving from Queries will not work it out from the UI,
and a feature nobody understands the point of is a feature nobody opens twice.

## Visualizations people can go wild with

**Custom visualizations in a notebook.** Open question, to be designed rather
than guessed: can Plotly be baked in and handed to people as "here it is, go
crazy"? What that costs in bundle size, what it means for the existing
viz-lib chart types, and whether a Python cell returning a Plotly figure is
the natural shape.

Investigate before committing. This is the item most likely to be bigger than
it sounds.

## Sharing a finished notebook

**Export as a PDF book**, from a button at the top. A notebook that has run is
a report; a report people cannot send is half a report.

**A public share link**, so somebody can be shown the thing without an
account. Same shape as a shared dashboard, and the same care about what a
public link exposes.

## How somebody finds out how to read a cell — done 2026-10-31

The question that exposed this: *how will the user know how to get data from a
particular cell?* Hiding the cell id left only the title on screen, so the name
a later cell has to type was nowhere a person actually was — the rule lived in
the help dialog and in no other place. Three answers now, in the three places
the question gets asked:

- **On the cell.** The name in monospace beside the title, one click to copy;
  renaming is in the ⋯ menu.
- **Under the editor.** "Reads from `orders`", with that name's columns in its
  tooltip. Only what really is readable: a name appears because a cell above
  handed over a *table*.
- **In the editor.** Autocomplete completes against the cells above and their
  columns, fed by `GET /api/notebooks/<id>/handoffs` over `Store.schema()`.
  Its own request, not part of the notebook payload — reading it opens the
  DuckDB file, which is the mistake bug-119 already made on this page.

**And the handle follows the title**, while the handle is still generated and
nothing refers to it yet, so there is one thing to fill in rather than two.

## To work out, not yet decided

**Simplifying data sources for somebody who already has access.** If a person
can already query a warehouse, how much of the data source picking can
disappear? Asked as an open question, not a specified feature.

**Read Zeppelin's UI properly** before building the layout items above. Most
of this exists there and has been through years of use; copying what works is
cheaper than rediscovering it.

**Where the schema browser goes** — the last of the query-window parity items,
and the one that decides the layout, so nothing else in it should start first.
Proposed: a tabbed sidebar, Contents / Schema, with the schema following
whichever cell has focus — a SQL cell against a warehouse shows that
warehouse's tables, a cell over earlier cells shows the handoffs. Asked three
times, not yet answered.

## Already answered during this round

**The Catalog is not missing from 0.8.** It is gated on MCP
(`Feature(MANAGE_CATALOG, ..., enabled=_mcp_is_on)`), so an install with
`mcp.enabled=false` offers neither it nor `use_mcp` and the nav drops both.
Admin is not the issue: `can()` passes any admin once the install offers the
feature. The minikube validation cluster now runs with `mcp.enabled=true`.

`send_dashboards` stays off there: it needs the `sqldesk-screenshots` image,
which is not published for this version.
