# Notebooks — the design argument

Iqbal's product statement, **2026-10-04**, and the design it settled.
Nothing is built yet. Every fork in §3 and §4 was **decided on 2026-10-04**;
§7 holds what that decision newly raised.

Read [0.8-plan.md](0.8-plan.md) first — notebooks are the headline of a
release that has six other items in it.

---

## 1. Why notebooks exist

His framing: a query answers one question, a dashboard tells a story with
several, and **both are SQL and only SQL**. A notebook tells a story in SQL,
Python or Scala.

The multi-language part is the *means*. Pitched as storytelling, a notebook
loses to a dashboard for telling stories and to Jupyter for everything else.
The thing it does that neither does:

> **A saved, re-runnable, permissioned chain of steps whose intermediate
> results are addressable.**

That is the gap, and it is the one 0.8-plan.md already named: the work that
does not fit in one SELECT happens on somebody's laptop today, so the lineage,
the permissions and the schedule all stop at the edge of it. Everything below
is in service of that sentence; a feature that does not serve it is 0.9.

## 2. What he asked for

- A notebook's **type is chosen up front** — Python or Scala — and all code
  cells are in that language. Picked from cards on the new-notebook page:
  *scalabook*, *pythonbook*, *sqlbook*, *mix*.
- **SQL cells** in any notebook, executing exactly as queries do today, and
  **only** against defined data sources.
- **Code cells** whose output is treated as a regular query result, so
  visualizations work on it.
- Code cells may reach **defined data sources** — with an easy way to see
  which ones the user has — or a **cluster**, where nothing is defined and the
  user writes the whole job themselves. We create the file, run it, and if it
  returns something we respect it as a result.
- A new data source type: **ETL Cluster** — Spark, Spark on YARN, HDFS, Ceph,
  more later, **one new cluster type per release**. Its own configuration,
  the way a Zeppelin interpreter has its own. Administrators define and add
  them.
- **Streaming sources are excluded.** A notebook runs on what is already
  configured; no stream setup to do.
- Every cell's output **persisted against the notebook** and long-lived — his
  words: DuckDB or something, but it has to live, like Postgres, with every
  cell hooked to a notebook id.
- **Referring to another cell's output** from Python, Scala or SQL, very
  easily.
- **Notebook controls**: run, stop, clear, hide code, hide output.
  **Cell controls**: run, clear output, hide code, hide output.
- The new-notebook page **says what can and cannot be done** — the idea of the
  product, stated.

Non-functional, and he put it first: **fast like a BI tool, easy like Jupyter,
UI like SQLDesk, interpreters like Zeppelin.**

## 3. The fork that decides the release

Two different products are hiding in "code cells".

| | **A — Notebooks orchestrate** | **B — SQLDesk gains a runtime** |
|---|---|---|
| Where code runs | On an interpreter: a cluster, or an optional sandboxed executor container | In the RQ worker process |
| What SQLDesk executes | Nothing of the user's | Arbitrary user Python |
| Blast radius of an escape | The executor: no DB credentials, no Redis, no data-source configs | Postgres credentials, every encrypted data-source config, the queue |
| New images | One optional executor, off by default | None |
| Precedent in repo | The 0.7 screenshots sidecar | `query_runner/python.py` |

**Decided: A.** The evidence is already in the tree.
`sqldesk/query_runner/python.py` does B — RestrictedPython, in-process — and
it is **deliberately absent from `default_query_runners`**
(`settings/__init__.py:356-403`). RestrictedPython is a sandbox in name; its
escapes are published, and an escape in our worker reaches the encrypted
configuration of every data source in the org. Making notebooks the headline
of 0.8 on that path means shipping as the flagship the one thing we currently
refuse to switch on.

A also *collapses* two of his bullets into one rule:

> **A code cell always runs on an interpreter. An interpreter is either a
> cluster an administrator configured, or the local executor.**

That is the Zeppelin model he asked for, and it is the permission boundary in
the same object. "Runs on a data source" stops being a third mode.

## 4. The problems worth designing before writing anything

### 4.1 Code cells do not reach data sources — **decided**

A code cell gets its data from an earlier cell in the same notebook. Nothing
else. Iqbal's words: *"you get data then you can play with it like you have
query results and all, playing with it in python in same book."*

This is the strongest decision in the design, for what it **deletes**:

- **No credential ever crosses the boundary.** There is nothing to scope,
  mint, expire or revoke. The render-pass-shaped token of the earlier draft is
  not needed in 0.8 at all.
- **The executor needs no route back to SQLDesk.** No API access, no network
  egress. It receives inputs, runs code, returns a result. A sandbox with
  nothing to reach is a sandbox rather than a promise.
- **The permission question answers itself.** A code cell can only see data a
  SQL cell was permitted to fetch, under the data-source permissions that
  already exist. No new access check is invented.

The cost is one real limit, and it belongs in the product rather than being
discovered: **a code cell cannot query, only compute.** Anything that needs
the warehouse needs a SQL cell above it. The picker and the empty-cell state
should say so.

### 4.2 Three lifetimes are hiding in "persist cell output"

Putting the handoff in Postgres is the trap: `query_results.data` is JSON in
one column, and notebook intermediates will be orders of magnitude larger than
a dashboard query's result.

| What | Size | Where | Lives |
|---|---|---|---|
| The **displayed** output | small, truncated | `query_results`, as today, keyed to the cell | with the notebook |
| The **handoff** between cells | arbitrary | per-notebook DuckDB file (local) or a cluster namespace (cluster) | until re-run; disposable |
| The **provenance** — cell, run, inputs, timing | tiny | Postgres rows | forever |

**Decided:** split them exactly like that. Reopening a notebook renders
saved outputs out of Postgres instantly and attaches nothing. Re-running
re-materializes the handoff. That is how both halves of "fast like a BI tool"
and "Jupyter-sized intermediates" are true at once.

**§4.1 makes this load-bearing rather than an optimisation.** If a code cell
can only get data from a SQL cell, the SQL cell is the notebook's only tap —
so it has to be able to hand over five million rows, which JSON in a Postgres
column cannot do. A SQL cell therefore writes **twice**: the full result into
the notebook store as the handoff, and a truncated slice into `query_results`
for display. One of those is for the next cell; the other is for your eyes.

The per-notebook DuckDB file is a third use of DuckDB after uploads and stream
windows — confine it the way `query_runner/duckdb.py:162-167` does
(`allowed_directories`, `enable_external_access=false`,
`lock_configuration=true`).

### 4.3 Cell references: name them, never number them

Precedent exists for both halves: the `query_results` runner already lets SQL
say `query_123`, and `python.py` already has `get_query_result(id)`.

- SQL cells see each earlier cell as a **relation**.
- Code cells get the same thing as a **dataframe**.
- **Cells are named, not numbered.** Numbering breaks the instant somebody
  inserts a cell above, and it is the single most common complaint about every
  notebook tool that does it.

### 4.4 Opening a notebook must not start an interpreter

A Spark session takes 30–60 seconds to come up. If opening a notebook attaches
one, nothing about the product feels like a BI tool, however fast the rest is.

**Rule:** opening renders saved output and shows the interpreter as *not
attached*. The first run attaches, and says up front how long that will take.
Same discipline as streams in 0.7 — a topic is consumed only while somebody is
watching.

### 4.5 Scala is a cluster feature, and should not gate the release

Python runs locally or on a cluster. Scala realistically only ever runs on a
cluster — nobody wants a JVM in our image — so *Scala* means *Spark is
configured*. **Decided:** SQL + Python in 0.8, with the interpreter
abstraction built so Scala is a registration rather than a rewrite; Scala in
0.8.x or 0.9. The picker then has two live cards and one that states what it
needs, which is the honest version of the page he wants anyway.

### 4.6 Stop has to actually stop

Three different cancellations hide behind one button: a running cluster job, a
running SQL query, and a queued cell. `CancellableJob`
(`sqldesk/tasks/worker.py`) covers the middle one. **Stop means** cancel the
current cell and do not start the next — not kill everything instantly, which
we cannot promise for a submitted Spark job.

### 4.7 An ETL Cluster is not a data source — **decided**

A data source answers queries; a cluster accepts jobs. We have six runners that
*query* a cluster (`hive_ds`, `impala_ds`, `presto`, `trino`, `drill`,
`databricks`) and **nothing that submits to one**. That is what this adds.

| | **(i) `DataSource` with a kind flag** | **(ii) Its own `Interpreter` model** |
|---|---|---|
| Free | encrypted config, group permissions, test-connection, the Settings UI | nothing |
| Cost | the query path must learn to ignore it: dropdowns, schema browser, MCP catalog | a table, a permission, a settings page, a serializer |
| Precedent | dashboard `kind` in 0.7 — same move, two weeks old | — |

**Decided: (i) for 0.8**, with eyes open that it is the thing most
likely to want extracting in 0.9. `DataSource` is already overloaded; the
partition discipline from 0.7 is what keeps it honest — a streaming source is
excluded from notebooks the same way a cluster is excluded from Queries.

### 4.8 A visualization on a cell is cheap; a widget on a dashboard is not

- **In**: cell output lands in `query_results`, so the existing visualization
  editor works on it unchanged.
- **Deferred**: a notebook cell as a *dashboard widget*. Refreshing a widget
  backed by cell 7 means running cells 1-7, on an interpreter, on a dashboard
  refresh interval. That is a scheduling design, not a widget.

### 4.9 "What can and cannot be done" is a rule, not a page

Zeppelin's failure mode is discovering limits by hitting them. A static page
describing the product goes stale in one release. Instead: the picker says what
each kind needs, and a cell says why it cannot run **before** it is run — no
interpreter attached, no cluster configured, that data source not permitted.

## 5. Scope — decided

**0.8** — SQL and Python cells; the local executor sidecar and one Spark
interpreter; named cell references; the split store; notebook and cell
controls; the picker; visualizations on cell output. **Read-and-look: nothing
in 0.8 writes back to a data source.**

**0.9** — Scala; writing back to a data source (ETL as the name promises);
scheduling a notebook; notebook cells as dashboard widgets; a second cluster
type; code cells reaching data sources directly, if it is ever actually wanted.

## 6. Decided, 2026-10-04

| Question | Answer |
|---|---|
| Where user code runs | **Not in our worker.** An interpreter: the optional local executor, or a cluster |
| Code cells reaching data sources | **No.** Data arrives from an earlier cell only |
| ETL cluster model | `DataSource` with a kind flag, excluded from the query path |
| Write-back in 0.8 | No — read-and-look |
| Scala | 0.9; the interpreter abstraction is built for it now |
| Cell output as a visualization | Yes |
| Cell output as a dashboard widget | 0.9 |
| Cell identity | Named, never numbered |

## 7. What that raised

### 7.1 Does a notebook have a session?

*"Play with it in python in same book"* implies Jupyter: `df` assigned in one
cell is still there five cells later. Two models, and they trade differently:

| | Session (Jupyter, Zeppelin) | Stateless cells |
|---|---|---|
| Feel | what people expect | foreign |
| Hidden state | yes — the reason notebooks rot | none |
| Re-runnable from cold | not guaranteed | by construction |

**Recommendation: a session, with a guarantee bolted on.**

- Variables persist across cells while an interpreter is attached. Jupyter's
  feel, unchanged.
- Every cell records which cells it read and when it last ran.
- A cell whose inputs have re-run since shows as **stale**, visibly, before
  you trust its number.
- The session dies on an idle timeout; reopening shows saved output and
  attaches nothing (§4.4). Re-running from the top must reproduce the
  notebook — and because §4.1 means every input is another cell's output,
  it actually can.

Zeppelin has the session and no staleness tracking, which is why Zeppelin
notebooks rot. That one addition is the difference between a notebook you can
believe and a notebook you have to re-run to believe.

### 7.2 Build order

1. **Model and store, no UI** — `Notebook`, `NotebookCell`, `NotebookRun` and
   the migration; the per-notebook store; a SQL cell writing both the handoff
   and the display slice. Needs no new container; testable entirely in pytest.
2. **The executor sidecar** — `Dockerfile.executor`, one route taking code
   plus inputs and returning a result, logs or an error. Resource-capped, no
   egress, off by default. Same shape as `Dockerfile.screenshots`, which is
   two weeks old and proven.
3. **Python cells** — shipping inputs to the executor, landing the result;
   session lifetime, idle timeout, staleness.
4. **The UI** — the picker, the notebook page, run/stop/clear, hide code,
   hide output.
5. **Visualizations on cell output** — close to free if 1 is right.
6. **The Spark interpreter** — the `DataSource` kind, its config, the submit
   path. Last on purpose: the local executor proves the abstraction before a
   cluster is needed to test anything.
